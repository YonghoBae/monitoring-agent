# 조회 도구 감사

2026-11-16, 운영 데이터를 변경하지 않고 코드·Prometheus 규칙·Docker inspect·Loki stream 레이블을 확인했다. 모델의 답변 실패는 아래 세 층으로 나누어 판단해야 한다.

| 영역 | 확인한 문제/경계 | 이번 조치 |
|---|---|---|
| PromQL 수치 전달 | `duration`에 포함된 문자열 `ratio` 때문에 6.2초를 620%로 변환. `_bytes`가 들어간 비율 표현식도 byte로 표시할 수 있음 | 임의 PromQL의 값에 자동 단위 변환을 적용하지 않음. 원시 수치와 표현식을 함께 반환 |
| 대상 구분 | range query 결과의 첫 시계열만 사용하고 레이블을 버림 | 최대 20개 시계열의 실제 레이블, 최근 표본 시각, 유효 표본 수, 절단 여부를 반환 |
| 레이블 탐색 | 이름 목록은 있지만 상세 조회 결과에 레이블이 빠졌음 | 수정된 range 요약과 `describe_metric`으로 실제 레이블을 확인 가능. 새 backend 데이터가 생긴 것은 아니며 탐색 편의 도구임 |
| 컨테이너 현황 | 기존 목록은 실행 중인 이름만 제공. 버전·health·OOMKilled·exitCode를 알 수 없음 | `inspect_container` 추가. 선택된 필드만 출력하고 Env/labels/전체 inspect는 노출하지 않음 |
| 컨테이너 로그 | 기존 도구는 `{job="docker"} |= 이름`. 실제 앱 로그 본문에 자신의 컨테이너 이름이 없으면 못 찾음 | 확장 조건의 `read_container_logs`가 Docker `.LogPath`를 조회해 Loki `filename`을 정확히 지정 |
| 로그 수집 구조 | 최근 1시간 Loki stream에 filename/job/service_name/stream은 있지만 container_id/container_name은 없음 | 실제 앱 Docker LogPath와 Loki filename 일치를 확인. 수집기 설정이나 운영 서비스는 변경하지 않음 |
| 로그 시간·분량 | 30줄, 줄당 300자 제한. 호스트 journal/kernel 전용 도구 없음 | 이번에 모두 해결하지 못한 범위로 기록. OOM 이벤트만으로 희생 프로세스를 단정하지 않는 사례 포함 |
| 관측 실패 | 접근 실패/빈 결과/정상을 구별해야 함 | Docker API 불가 사례와 unknown 채점, 없는 근거로 정답을 추측하면 점수 없음 |

원래의 `query_loki`는 비교의 기존 도구 조건에 남겼다. 확장 조건만 새 로그 조회를 갖는다. 합성 로그의 인위적인 이름 접두사를 제거했으므로 기존 도구에서 실패가 드러날 수 있다. 이는 모델에게 정보를 다르게 숨기는 임의 설정이 아니라 실제 도구의 검색 계약을 재현한 것이다. 다만 이 사례 모음에서 로그 장애 비율은 실제 발생 빈도를 의미하지 않는다.

Docker 조회는 shell 문자열 실행 없이 `ProcessBuilder` 인자로 전달하고 컨테이너 이름을 검사한다. 5초 시간 제한과 출력 크기 제한이 있다. 로그 경로는 Docker가 반환한 값을 JSON 문자열로 인코딩해 LogQL에 넣는다. 중지된 컨테이너도 inspect가 가능하지만 삭제된 컨테이너·외부 로그 드라이버·Loki 보존 기간 밖의 로그까지 복원하는 기능은 아니다.

아직 부족한 관측은 compose 의존성·볼륨/네트워크, 공유기/VPN 라우팅, 실제 DNS/TLS 검증, SMART/RAID/UPS, systemd journal/kernel, 프로세스별 CPU/메모리, DB 실행계획/락 그래프, 백업 복원 검증이다. 이 정보가 없는 상황에서 특정 원인을 확정하도록 프롬프트만 강하게 만드는 것은 해결책이 아니다.

평가에서 관측해야 할 실패 유형은 ① 도구에 정보가 없음 ② 도구가 잘못 요약함 ③ 모델이 필요한 도구를 쓰지 않음 ④ 조회한 값을 잘못 해석함 ⑤ 원답은 맞지만 출력 형식을 어김으로 분리한다.
