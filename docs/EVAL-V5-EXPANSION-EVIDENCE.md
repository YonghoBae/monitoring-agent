# Additional homelab mechanism candidates

Research date: 2026-11-17. Independent AI source review; no human validation, reproduction, production change or paid model call. This package is separate from the frozen v5 comparison. It does not add cases, alter gold or increase the reported incident count.

Three candidates are useful for a next evaluation round: published-port conflict, container DNS identity mismatch, and archive self-inclusion causing storage exhaustion. All have public diagnostics plus a concrete correction supported by a reporter, a demonstrated comparison or maintainer code. Their confirmation strengths differ. None is ready-made production telemetry with independently established normal/fault/recovery gold, and none establishes how frequent these problems are in this homelab.

## 1. Published-port conflict: Pi-hole issue 1657

**Source chain.** The original report concerns Pi-hole previously working on Unraid 6.12.11, then failing during container startup. Docker reports a bind collision for host TCP 443. After removing that unnecessary mapping, the reporter supplies the same error for TCP 80. A maintainer explains the host publication conflict; the original reporter later says restoring the custom-interface setting with a separate IP made Pi-hole work again. This is a naturally encountered configuration incident, not an injected benchmark fault. [Original report](https://github.com/pi-hole/docker-pi-hole/issues/1657), [second diagnostic](https://github.com/pi-hole/docker-pi-hole/issues/1657#issuecomment-2461112746), [maintainer explanation](https://github.com/pi-hole/docker-pi-hole/issues/1657#issuecomment-2461139573), [reporter-confirmed correction](https://github.com/pi-hole/docker-pi-hole/issues/1657#issuecomment-2463208446).

The demonstrated direct failure is host address/port binding. Do not infer Apache, nginx, a particular Unraid process, or an OS update as the proven competing cause: those were suggestions, not process-owner evidence. Removing 443 did not solve the subsequent 80 conflict. The final network setting is partly shown in a screenshot, which this audit did not independently inspect; its exact driver/configuration must not be invented. Success is reporter testimony without a post-fix packet trace or DNS probe. Issue closure adds no extra proof.

**Next reproduction.** For a faithful publication test, use a disposable Docker daemon/VM with two toy services competing for a selected address/port, then change only the publication endpoint and confirm a client request. Capture daemon startup stderr, both publication configurations, a timestamped listener-owner observation, failed start state and recovered service probe. A cheaper isolated-network-namespace socket bind conflict is feasible as an adaptation, but it would test socket occupancy rather than Docker host-publication behavior and must be labelled accordingly. Do not reserve production 53/80/443 or switch the homelab's interfaces merely to recreate this source.

**Gold/tool contract.** Error-only evidence supports “bind failed because that address/port was already in use”; exact listener ownership requires the new observation. Current selected `inspect_container` ports plus application logs may miss a daemon-side failure that happens before the application starts. A deployment-event record and bounded listener inspection would be needed. Partial controls should withhold the daemon diagnostic and require unknown cause, not assume every failed start is a port collision. [Docker's publication documentation](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/) confirms the host/container port distinction and optional host address; it is behavior documentation, not incident evidence.

## 2. DNS identity/alias mismatch: Compose issue 2925

**Source chain.** The issue includes a minimal configuration with a custom bridge and an internal hostname, then a failed ping to that hostname. An inspection comment lists the service-name and short-ID aliases. A maintainer describes the alias policy at that time. Another participant supplies a concrete failed hostname-only test and successful container-name test on an overlay network; the original reporter acknowledges that their supposedly contrary shell example also set the container name. This is a naturally reported configuration misunderstanding with subsequent controlled diagnostic demonstrations, not a verified production outage. [Original example](https://github.com/docker/compose/issues/2925), [alias inspection](https://github.com/docker/compose/issues/2925#issuecomment-184431003), [maintainer explanation](https://github.com/docker/compose/issues/2925#issuecomment-184758886), [paired demonstration](https://github.com/docker/compose/issues/2925#issuecomment-184967460), [reporter acknowledgment](https://github.com/docker/compose/issues/2925#issuecomment-185285625).

The successful demonstration uses overlay networking while the initial Compose example uses a bridge. Later comments span different versions and contain inconsistent additional reports. Do not combine them into one controlled before/after deployment, assert all modern `hostname` settings behave identically, or interpret name-resolution failure as proof of firewall failure. The supported historical correction is to use a registered identity rather than assume that setting the process hostname supplies the desired DNS identity.

**Next reproduction.** Prefer a current isolated user-defined bridge with two fixed-image containers. Capture their network membership and alias sets, show an existing peer service reachable by its valid name/IP, request one deliberately unregistered alias, then register only that alias and repeat name lookup plus an application-level probe. Keep resolver, peer process and network membership constant. This makes the next case a clearly declared missing-alias adaptation, not an exact recreation of a 2016 Compose behavior. An IP-success/name-failure observation helps distinguish name resolution from general reachability; it still does not by itself prove why the name is missing. [Current Docker bridge documentation](https://docs.docker.com/engine/network/drivers/bridge/) supports name/alias resolution on user-defined bridges.

**Gold/tool contract.** Require resolver output and selected network/alias inspection before scoring an exact missing-alias cause. Existing `inspect_container` does not expose those fields and no current generic DNS probe tool supplies the paired test. Logs alone may show only a resolution error, which warrants a narrower gold. Partial views must not retain an injection name such as `missing-alias` or hidden network metadata. A successful corrected probe proves this connection, not the entire network or every DNS path.

## 3. Storage exhaustion from dump self-inclusion: Gitea issue 27424

**Source chain.** An operator using Gitea 1.20.5 on Ubuntu reports a growing archive much larger than the source tree when dumping from the configuration directory. A second participant supplies a containerized invocation whose log names the archive itself as the file being packed when the write runs out of space. A maintainer identifies output-inside-data as the mechanism and recommends placing output outside Gitea's directories, while explicitly limiting the scope of a linked fix. The merged PR adds global exclusion of the output archive path and corresponding tests. These are encountered operator failures plus a maintainer-supported correction, not a claim that the original reporter published successful recovery telemetry. [Original report](https://github.com/go-gitea/gitea/issues/27424), [container diagnostic](https://github.com/go-gitea/gitea/issues/27424#issuecomment-1766284616), [maintainer correction](https://github.com/go-gitea/gitea/issues/27424#issuecomment-2033423119), [merged repair](https://github.com/go-gitea/gitea/pull/30240).

The archived PR is merged at commit `654cfd1dfbd3f3f1d94addee50b6fe2b018a49c3`. Its diff adds `dumper.GlobalExcludeAbsPath(outFileName)` and an exclusion test. This is stronger than closure alone but not a proof that every path/symlink/storage configuration or released image is fixed. The initial author used a console/snap-style path; the ENOSPC diagnostic comes from a different containerized deployment. Keep those identities separate. No inode/byte-usage snapshots accompany the quoted container failure, so ENOSPC alone would not distinguish all capacity limits without the archive-path evidence and new filesystem observations.

**Next reproduction.** Use a tiny Gitea fixture and a strictly bounded disposable storage volume, with an independent output-size/time cutoff. First save an archive outside the input tree and verify its contents. On an affected pinned build, place output within the archived tree and capture source/output paths, archive-entry progression, available bytes/inodes and the failure or explicit safety-stop outcome. Then move only the output destination outside the input tree and verify completion, bounded size and required archive entries. Separately test the merged exclusion behavior if desired; do not change output location and binary simultaneously and call it one-variable recovery. A safety-stop observation must not be relabelled as an observed ENOSPC. No full host disk, production repository, unrestricted recursive growth or deletion is needed.

**Gold/tool contract.** A generic full-storage log supports a capacity failure, not archive self-inclusion. That cause requires evidence that the output archive is itself selected for inclusion and grows while packing. Current tools lack archive-job metadata and path/entry inspection; source collector additions should expose bounded sanitized records. Successful archive creation is not restoration proof. This adds a storage/path mechanism beyond PostgreSQL even though backup workflows remain a shared theme.

## Cached-image feasibility and acceptance gates

The existing capture records PostgreSQL 16.16 Debian and 17.12 Alpine image IDs. That establishes their availability during the earlier capture, not that all proposed images remain cached now. No Pi-hole, Gitea, Alpine-only or BusyBox cache was verified in this research. Do not promise an exact source-version reproduction without checking image presence/digests and required utilities.

The captured PostgreSQL images could potentially host the two tiny network peers and use `psql` connection attempts for a DNS/application probe. That is an adaptation of the network mechanism; it does not add service diversity merely by reusing PostgreSQL. A successful probe needs a deliberately configured isolated test server, and client tools/utilities should be checked first. Exact Pi-hole publication and Gitea self-inclusion reproductions require their own pinned images or a declared minimal surrogate. A generic file copy into bounded tmpfs would prove bounded storage exhaustion, not the Gitea archive-selection bug.

Before any candidate enters the next dataset: capture healthy/fault/recovered outcomes; isolate the claimed intervention; preserve raw commands, outputs, versions and hashes; prove the agent can reach the decisive evidence through equal tools; define the unknown-cause view; and obtain independent gold review. Keep family labels and intervention names out of model input. These are future acceptance gates, not work performed during the frozen comparison.

In particular, an ENOSPC message is not universally proof of full disk bytes, and exit 137 alone would not prove a cgroup OOM. No OOM family is newly validated here.
