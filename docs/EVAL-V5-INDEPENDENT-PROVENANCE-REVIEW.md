## Confounds and evidence limits

- **The pg_dump intervention changes an image, not solely a version number.** `environment.json` records PG16 Debian trixie and PG17 Alpine. The explicit diagnostic plus successful before/after dumps strongly supports the immediate mismatch cause; it does not establish a binary-only controlled experiment or general performance comparison. Keep `phases.json` wording at “client image changed”; do not promote it to “all other client variables held constant.”
- **A second permission message is a nuisance signal, not the demonstrated cause.** Events 43, 52 and 67 all contain `chmod: /var/run/postgresql: Operation not permitted`, including successful normal and recovered initialization. The discriminating fault is the unreadable SQL file. A scorer that accepts a generic permission-error explanation or the socket-directory warning as the cause would reward the wrong diagnosis.
- **Precise Unix ownership attribution is collector knowledge.** The script records host file UID/GID 1000 and mode 0600 in `phases.json`; mode changes occur in Python, outside the Docker event stream. The failed container's numeric effective identity and an in-container `stat`/read test are not recorded. The controlled chmod sequence and named error support unreadable SQL; logs alone do not distinguish every DAC, ACL or security-policy explanation. Gold requiring exact owner/mode must expose appropriate evidence or score that claim as unknown.
- **Restoration verification is deliberately small.** Events 22/28 verify count 3 and sum 60 after successful SQL restoration. This does not prove every row value, full-schema fidelity, production backup completeness, durability, point-in-time recovery or remote storage delivery. The original source server remains alive; restored databases are on that same disposable server. No original production data-loss sequence is reproduced.
- **Readiness is adequate for this capture but weaker in the reusable script.** `wait_server` accepts socket readiness plus marker count 3 (`:75-82`), which can occur during the temporary initialization server. Actual logs 43/67 show final initialization completion and final server startup; future captures should explicitly assert that stage if claiming persistent service recovery. No long-duration stability or post-restart persistence is tested.
- **Reproducibility metadata is partial.** Captured image IDs pin the local run, but the script starts future runs from mutable tags (`:16`, `:124-126`). There are no registry pull digests, Docker/kernel/platform metadata, generating-script hash, or captured stdin/hash for the restoration commands (`:31-39`, `:103`). Dump output exists in events 19/25 and the script shows its use, so this does not negate the captured restore evidence; it limits exact replay and independent audit. The validation JSON is generated by the same code whose assertions it summarizes, not an independent checker. Python assertions also disappear under optimized execution.
- **Isolation is supported within the recorded scope.** Commands use the internal temporary network, no published ports, only the temporary SQL bind, bounded resources and disposable tmpfs storage. Cleanup events 76/77 return no matching containers/network. All five listed SHA-256 hashes match. The `production_modified=false` metadata is still a program assertion, not a whole-host audit. UTC timestamps on November 16 correspond to November 17 in Korea and are not an artifact-date contradiction.

## Contamination and adaptation constraints

The source incidents and diagnostic phrases are public and potentially familiar to pretrained models. Independent review cannot establish training-data exclusion. These are source-backed adaptations with newly captured observations, not private unseen incidents. The two families share PostgreSQL, use three-row data, and were selected for easy local reproduction. Their success says nothing quantitative about prevalence or representativeness across home-server incidents. Normal/fault/recovered/partial variants are correlated views, not independent incident samples.

Keep source URLs, gold labels, `phases.json`, the reproduction script and container names such as `init-fault`, `init-recovered` and `client-mismatch` out of diagnostic model views unless intentionally evaluating interpretation of an already-labelled test report. Raw event argv includes these names. A partial view that hides the diagnostic but leaves its phase or injection name is not an honest uncertainty test. Build frozen, phase-local views, inspect prompts and tool outputs for those leaks, and group evaluation/tuning splits by family. Do not use new family outcomes to tune prompts and then describe the same cases as held out.

The collector uses Docker inspect/logs, pg_dump execution, SQL queries and host file metadata. Collection capability does not establish the operational agent's capability. If an arm only has monitoring metrics or logs, direct SQL results, client versions and file permissions may be unavailable. Publish a per-field tool/evidence availability map, distinguish unavailable tools from agent errors, and evaluate a replay adapter as replay rather than live operational competence. In partial views, “unknown” must be justified by exactly what is visible, not merely by deleting one selected string while retaining other decisive evidence.

The source/view/gold package has passed this content review and is ready to freeze under `docs/EVAL-V5-PROTOCOL.md`. Actual execution readiness still depends on the separate runner input/tool-boundary validation and campaign manifest. The present evidence supports a small two-mechanism development core, not dataset sufficiency or a general harness ranking.
