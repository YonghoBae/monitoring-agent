# 출처, 정답, 비교 조건

실행 완료 결과는 [최종 보고서](EVAL-V4-RESULTS-2026-11-16.md)에 있다. 실행 원본은 보관했고 현재 재사용 데이터는 gold 한 값을 고친 revision 4.1이다.

2026-11-16에 v4 40개 사례를 고정했다. Google SRE의 가설 검증 절차, Brendan Gregg의 USE Method, Prometheus 알림/규칙 테스트 문서, Docker inspect 문서의 원문과 SHA-256을 `eval/v4/sources.json`에 보관한다. 이 문서들은 **진단 방법의 근거**다. 각 합성 사건이 실제로 발생했다는 근거는 아니다.

AIOpsLab의 실제 target-port 문제 정의, registry, MIT 라이선스를 커밋 단위로 `eval/v4/public-benchmark/`에 보관한다. 해당 문제의 Kubernetes Service targetPort 오류를 Docker published port와 앱 listen port의 불일치로 변형한 사례와 정상 대조군을 추가했다. 원본 벤치마크를 그대로 실행하거나 AIOpsLab 점수를 재현한 것은 아니다.

## 데이터 구성

- 운영 Prometheus에서 읽은 58개 알림 규칙 정의를 고정하고, 선택한 알림의 실제 표현식/레이블/지속 시간으로 통제 관측을 검증했다.
- CPU·RAM·디스크 공간/IO·GPU·OOM·컨테이너·인증서·DNS/외부 HTTP·SSH·시계·백업·알림 전송·systemd·DB 로그를 다룬다.
- 알림 없이 현재 수치나 서버 정보를 묻는 질문, 이미 복구된 상태, 자료 부족, Docker API 실패, 로그에 섞인 지시문, 정상 포트 설정 대조군을 포함한다.
- 3개 컨테이너의 이미지/상태/health는 실제 서버의 비밀 필드를 제외한 snapshot이다. 해당 질문의 기준 시각은 snapshot 수집 시각이다.
- 기존 v3 관측을 재검토해 활용한 사례는 provenance에 남겼다. 실측 장애 로그/메트릭 타임라인으로 복원된 사고 사례는 **0개**다. 이전 DB 감사에서 resolution 연결이 없어서 원인을 확정할 수 없었다.

모든 수치 정답은 격리된 실제 Prometheus에서 쿼리하거나 원문 로그의 값을 대조했다. 알림의 `for` 조건은 60초 간격 전체 창에서 확인했다. 이는 전체 Prometheus 알림 상태기계 테스트와 같지 않다. 범주형 원인은 통제된 로그·설정의 의미를 검토한 정답이며 독립적인 사람 검수는 아직 없다.

## 비교 설계

모델은 `qwen3.5:9b-pi32k`, context 32768, temperature 0, reasoning off, 응답 최대 1536 tokens, 도구 12회, 요청 90초다. 실제 모델 digest, pi 버전, 소스/데이터 해시는 campaign manifest에 저장한다. 요청은 직렬 실행하고 사례별 arm 순서는 고정 seed로 섞는다. 원답과 관측 trace를 먼저 저장한다.

진행 중 사용자의 GPU 확인 요청에 따라 같은 원격 endpoint `127.0.0.1:11434`의 `/api/ps` 및 `ollama ps`를 읽었다. 모델 적재 크기 7,336,078,865 bytes 중 VRAM은 5,712,463,789 bytes였고 CLI는 **CPU22%/GPU78%**를 표시했다. 이는 적재 비율이며 순간 GPU 사용률이나 연산 시간 비율이 아니다. 100% GPU 평가가 아니고, 전 실행 구간의 연속 하드웨어 측정도 아니다. 관측 원본 요약은 campaign의 `hardware-observation.json`에 있다. 따라서 지연 수치는 이 실행 환경의 결과로 한정한다.

| 조건 | 실행 경로 | 관측 도구 |
|---|---|---|
| production | 실제 ReAct v4 + Reflection / 실제 ConversationAgent | 기존 도구; native 검색·대화 도구 포함 |
| pi | 설치된 pi CLI, 내장 셸/파일/MCP 등 비활성화 | 공통 AgentTools |
| pi_plus | 같은 pi CLI | 공통 도구 + 실제 레이블/컨테이너 상세/filename 기반 로그 조회 |
| compact_plus | Spring AI 단일 대화 흐름, 별도 Reflection 재시작 없음 | pi_plus와 같은 도구 |

pi와 compact에 전달하는 핵심 시스템 지시는 같다. pi 자체 wrapper가 있으므로 전체 wire prompt가 byte-identical한 것은 아니다. production 비교는 제품 경로 전체의 차이다. pi_plus/compact_plus 비교는 같은 관측 도구를 가진 하네스 비교다. production의 명령 도구는 mock이며 실제 운영 명령은 실행하지 않는다. snapshot 질문은 기존 도구에 정보가 부족한 상황도 의도적으로 포함한다.

개발군 5개는 CPU family, 외부 사이트 장애, DNS 지연으로 구성했다. 초기 5조건 비교에서 PromQL 요약기가 `duration`의 부분 문자열 `ratio`를 백분율로 오인해 6.2초를 620%로 전달하는 오류를 발견했다. 임의 PromQL 결과의 자동 단위 변환을 없애고 원시 값·레이블·최대 20개 시계열·표본 시각을 보존하도록 고쳤다. 이전에는 첫 시계열만 반환하며 레이블도 버렸다. 이 공통 도구 수정은 이후 **모든 조건에 동일하게 적용**한다. 초기 개발 결과와 수정 후 결과를 혼합하지 않는다.

추가 운영 관측 감사에서 Loki에 container name/id 레이블이 없고 `filename` 레이블이 있다는 것을 확인했다. 기존 `query_loki`는 본문에 이름이 들어 있다는 가정으로 검색하므로 로그를 놓칠 수 있다. 확장 조건에는 Docker의 실제 `.LogPath`로 filename을 지정하는 `read_container_logs`를 추가했다. 앱 컨테이너의 LogPath와 실제 Loki stream filename의 일치도 확인했다. 데이터의 인위적인 `컨테이너명 |` 접두사를 제거해 이 관측 차이가 숨겨지지 않게 했다. 기존 도구는 원래 행동을 평가하도록 유지했다.

read-only 후보에서는 대화 승인 표현 필터를 제거했다. 조회 전용 후보에는 승인 도구가 없으며 이 필터가 일반적인 yes/no 답을 지울 수 있기 때문이다. 개발군에서 후보가 전체 컨테이너 상세를 탐색하다 예산을 소진하고, 답변용 `dns_seconds` 별칭을 실제 메트릭명으로 착각하는 것을 확인했다. 공통 핵심 지시에 요청 항목의 직접 관측 우선·원인 불명 시 종료를 추가하고, 모든 조건의 질문에서 출력 key가 실제 메트릭명이 아님을 설명했다. 정답 수치나 사례별 쿼리는 추가하지 않았다.

도구 수정 전 또는 개발 검토가 끝나기 전에 테스트가 자동 시작된 campaign `20261116-200105`, `20261116-200923`는 초반에 종료했으며 최종 점수에서 제외한다. 이후 `--phase dev`와 `--phase test`를 분리한다. 개발 확인 2조건과 나머지 35개 테스트 사례의 4조건 비교를 수행하고 각 실행 전후에 소스·데이터 해시를 검사한다. test 결과를 보고 같은 test에서 프롬프트를 조정하지 않는다. v3 관측을 이미 봤고 중단한 run에서 일부 테스트 출력을 확인했으므로 완전히 미공개인 독립 blind test라고 부르지 않는다. 각 조건 1회이며 작은 차이는 반복 검증이 필요하다.

추가로 합성 알람 문구에 남아 있던 임계값/지속 시간 설명을 제거하고 고정된 실제 운영 규칙의 summary에 실제 레이블을 대입했다. 예를 들어 지연 3초·GPU 메모리 95%라는 이전 설명은 실제 5초·90% 규칙과 달랐다. 이 정정 도중 수행한 `20261116-201603` 개발 run도 해시 검사로 제외했다. 최종 후보와 입력 계약을 선택한 뒤에는 개발 확인과 test를 `--phase all`로 연속 실행하되 그 사이 추가 튜닝을 하지 않는다.

`20261116-202252`의 개발 원답 검토에서 재생 기준 시각과 도구의 `observed_at` 실제 실행 시각이 섞이는 것을 확인했다. 과거 표본을 모델이 현재 표본으로 해석해 기준 시각의 답을 거절했으므로 이 run도 제외한다. 최종 러너는 네 조건 모두 관측 시각을 fixture 시각으로 고정하며, 실행 예산은 별도 실제 clock으로 제한한다. 운영 기본 clock은 바뀌지 않는다. 마지막 CPU 개발 사례를 간단 확인한 뒤 소스·데이터를 다시 고정한다.

## 점수 해석

`scores.json`은 JSON 형식으로 제출한 필드의 정확한 값/수치 허용오차와 관련 관측 도달 여부를 채점한다. 이것은 출력 계약까지 포함한 점수다. 내용은 맞지만 JSON을 생략한 답변도 있으므로 이 수치를 그대로 답변 정확도라고 부르지 않는다.

별도 `content-scores.json`은 원답의 정확한 인용을 남긴 모델 보조 추출을 같은 결정적 기준으로 채점한다. 추출 인용이 원답에 존재하고 모든 출력·필드를 검토했는지 검사한다. 독립적인 사람 채점은 아니다. `evidence_all` 필드는 관련 설정과 로그를 모두 조회해야 한다. 조회 실패는 unknown 답의 근거가 될 수 있지만 정상 판정의 근거가 될 수 없다.

단순 도구 이름 매칭에는 한계가 있다. 예를 들어 입력의 systemd unit 이름에 대해 `verify_alert`가 CONFIRMED를 반환했으면 동일 unit 메트릭을 다시 조회하지 않아도 이름과 실패 상태가 뒷받침된다. 내용 검토에서는 이런 대체 근거를 실제 observation ID와 이유를 남겨 명시적으로 인정하거나, 관련 메트릭을 읽었어도 계산 근거가 부족하면 기각할 수 있다. 원래 자동 근거 점수도 각 행의 `strict_evidence_score`에 보존한다. 원답 해시와 인용·관측 ID가 맞아야 채점한다.

“인덱스 누락이 검증됐는가”에 대한 `no`는 “인덱스가 정상이다”와 다르다. 실제 조회가 비었고 검증 근거를 확보하지 못했다면 전자의 답은 타당하다. 이런 경우만 `scope=absence_of_verification`과 실제 관측 ID·이유를 명시해 empty 관측을 인정한다. 빈 조회로 정상 상태를 인정할 수 없도록 검증한다.

요청값 일치, 근거를 확인한 항목 점수, 근거 없는 단정이 발견된 답변 수를 구분한다. 시간 초과 후 반환된 관측 요약에 요청값이 명시되어 있으면 내용 추출은 가능하지만 정상 완료로 취급하지 않으며 종료 사유·지연을 별도 보고한다. 초당 `rate`를 15분 증가 횟수 대신 답한 경우는 요청량을 답하지 못한 것으로 처리한다. [Prometheus 함수 정의](https://prometheus.io/docs/prometheus/latest/querying/functions/)와 [cAdvisor 지표 정의](https://github.com/google/cadvisor/blob/master/docs/storage/prometheus.md)는 이러한 단위 검토의 추가 근거다.

두 점수 모두 자유 서술 전체의 사실성, 제시한 모든 원인·조치의 타당성, 실제 복구 성공률을 의미하지 않는다. 시간 초과와 도구 실패, 형식 준수, 원답에서 발견한 과잉 단정은 별도로 검토한다.

최종 원답 감사에서 `jellyfin_transcode_cpu.encoding`의 원래 정답 `software`가 로그로 뒷받침되지 않음을 발견했다. 로그 두 줄은 트랜스코딩 시작과 출력 codec만 보여주며 encoder나 가속 방식이 없다. 수치 검증과 로그 존재 확인만으로 범주형 정답의 의미가 검증되지 않는 실제 결함이다. 원본 데이터·출력 계약 점수는 보존하고, 별도 `review-exclusions.json`에 데이터 해시와 이유를 기록해 **모든 arm의 내용 점수에서 같은 필드를 제외**한다. 해당 사례의 CPU 사용량 필드는 계속 평가한다. 정답을 맞힌 것처럼 보이는 `software` 답도 근거 없는 단정으로 검토한다. 이는 사후 데이터 품질 정정이며 사전 등록된 독립 평가라고 부르지 않는다.

fixture는 모든 도구에 완전한 서버 복제본을 제공하지 않는다. 상세 정보가 명시되지 않은 컨테이너의 `inspect_container`는 unavailable을 반환하며, 이는 실제 홈서버 Docker API가 실패했다는 뜻이 아니다. 따라서 불필요한 전체 컨테이너 순회가 예산을 소모하는 현상은 비교할 수 있지만, 이 결과로 실서비스 inspect 성공률을 계산할 수 없다. Loki fixture는 지정 컨테이너의 로그에서 기존 본문 검색과 filename 검색을 구별한다. 기존 본문 검색이 다른 컨테이너의 같은 문자열까지 잘못 찾는 false positive는 재현하지 않는다. Prometheus는 실제 엔진을 쓰고 상대 조회 기간을 fixture 기준 시각으로 이동하며, 다른 backend는 통제된 응답을 사용한다.

## 남은 범위

RAID/SMART, UPS, 공유기/DHCP/Wi-Fi, VPN/tailscale 경로, 실제 DNS/TLS 핸드셰이크, compose 의존성/볼륨/네트워크 관계, 백업 복원 성공, DB 쿼리 계획/락 그래프, 권한·보안 사고, 다중 동시 장애, 장기간 추세, 재시작 이후 복구 검증, 다회 대화와 승인 후 실행은 이 40개로 포괄하지 못한다. 특히 단순 시스템 수치만으로 원인을 확정할 수 없는 영역은 관측 도구 확장과 실제 사고 기록이 필요하다.

개선 후보는 `agent.investigation-mode=focused`, `agent.discovery-tools-enabled=true`로 알림 조사 경로에서 선택할 수 있다. 기본값은 기존 경로다. 대화형 명령·메모리 경로 전체를 교체하거나 운영 서비스를 재배포하지 않았다.

모든 모델 비교가 종료된 뒤, 동일 discovery 설정으로 ConversationAgent에도 새 조회 도구를 전달하도록 연결했다. 기본값 false는 유지한다. 실제 Spring tool loop에서 도구 노출·inspect 호출·승인 미생성을 회귀 검증했다. 이 후속 통합의 활성화 상태는 위 네 조건 중 별도 점수로 측정하지 않았으며, 단일 흐름 후보의 일반 질문 점수와 혼동하지 않는다.
