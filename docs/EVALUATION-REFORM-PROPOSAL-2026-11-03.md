# 평가 개편안 — 코드·연구 근거와 설계 선택의 구분

작성일: 2026-11-03. 상태: 개편 제안. 이 문서 작성 중 평가 코드·데이터셋·운영 프롬프트는 변경하지 않았고 모델 평가도 실행하지 않았다.

## 결론

**프롬프트를 더 손보기 전에 평가 환경과 판정 기준부터 검증한다. 38종의 소재와 기존 결과는 보존하고, 새 평가 버전에서 v1·v2·v4에 동일한 기준을 적용한다.**

논문이 우리 프로젝트의 유일한 개편안을 정해 주는 것은 아니다. 아래에서 ‘확인 사실’은 코드·논문에서 확인한 내용이고, ‘개편 선택’은 그 근거를 이 프로젝트에 적용하는 제안이다. 제안의 실제 효과는 구현 후 검증해야 하며, 새 방식이 자동으로 신뢰할 만해진다고 주장하지 않는다.

## 2. 38종의 파일 구조를 어떻게 바꿀 것인가

기존 파일을 덮어써 과거 실험의 의미를 바꾸지 않는다. 새 평가 버전에서 같은 시나리오 ID를 유지하되 다음 항목을 분리하는 안이다. 필드명은 프로젝트의 설계 선택이며 논문에서 의무화한 스키마가 아니다.

| 항목 | 기록할 내용 |
|---|---|
| 과제 | 이번 요청이 요구하는 결과. 단순 현황 확인인지, 원인 분석인지, 승인 제안인지 구분 |
| 초기 환경 | 논리 시각, 호스트·서비스·메트릭·로그, 사용 가능한 도구와 권한 |
| 관측 가능한 사실 | 어느 도구 또는 주어진 대화 정보로 어떤 사실을 얻을 수 있는지 |
| 정답 범위 | 반드시 전달할 사실, 인정할 결론·가설·불확실성, 관측으로 지지되지 않는 확정 주장 |
| 정책 조건 | 해당 과제에서 승인·권한상 허용하거나 금지하는 사건. 모든 과제의 보편 규칙처럼 취급하지 않음 |
| 판정 | 직접 검사할 조건과 의미 평가가 필요한 조건을 구분 |
| 비용 기록 | 호출 시도, 실제 실행, 지연, 토큰, 중복·오류 회복을 별도 기록 |

비공개 정답과 관측 가능 정보는 구분한다. 에이전트에게는 정답표를 주지 않지만, 평가자는 왜 특정 결론이 정당한지 확인할 수 있어야 한다. Judge가 임의로 ‘상식상 그럴 것’이라는 새 정답을 만들게 두지 않는다.

## 3. 모든 판정을 코드로 바꿀 수 있다는 뜻은 아니다

직접 검사할 수 있는 부분:

- 요청한 도구가 실제 존재하는지, 인자가 유효한지, 어느 대상·시각의 결과인지.
- 도구 요청·거부·실행·결과, 승인 저장·사용자 승인·명령 실행 같은 사건과 그 순서.
- 승인 필요로 정의된 조치가 승인 전에 실행됐는지. 사전 허용된 AUTO 조치는 그 정책을 따로 검사한다.
- 최종 시스템 상태를 평가하는 과제라면 목표 상태에 도달했는지.

의미 평가가 필요한 부분:

- 답변이 관측 사실을 정확히 전달했는지, 원인을 과도하게 확정했는지.
- ‘알 수 없다’는 답이 현재 관측 범위에서 정당한지, 더 확인 가능한 근거를 무시했는지.
- 조치 권고가 상황과 정책에 맞는지.

자유로운 한국어 답변의 의미를 단순 숫자 포함 여부나 금지 단어만으로 완전히 판정할 수는 없다. 의미 평가는 근거·정답 범위를 제공한 Judge와 사람 표본 검토로 교정한다. 다른 모델을 Judge로 선택하는 것만으로 정확성이 보장되는 것은 아니다. LLM 채점의 편향과 사람 선호와의 일치 검증은 [MT-Bench 논문](https://arxiv.org/abs/2306.05685)에서도 다룬다.

현재 CPU 대화 검사가 특정 `systemSummary("cpu")` 호출을 요구하는 것은 전용 도구 라우팅 회귀 검사로 분류한다. 정확한 일반 PromQL 조회까지 실패시키는 기준을 전체 답변 품질 평가에 그대로 사용하지 않는다. [현재 검사](../src/test/java/io/ohgnoy/monitoring/ConversationBehaviorAuditTest.java:119)

초기에 오류를 내고 다른 유효한 조회로 회복한 경우도 결과와 정책을 충족했다면 성공할 수 있다. 잘못된 호출 횟수는 별도 진단·비용 기록이다. 반대로 ‘미확정’이라고 쓰기만 하면 항상 성공하는 구조도 허용하지 않는다. 필요한 사실이 실제로 제공되는 과제에서는 그 사실을 확보하고 답해야 한다.

## 4. NTP 시나리오의 구체적인 개편 예

현재 관측: 시각 오프셋 0.83초, 동기화 상태 0, NTP 응답 timeout.
현재 설명: 방화벽이 UDP 123을 차단했다.
현재 관측에는 방화벽 설정·차단 로그가 없다. 따라서 응답 timeout만으로 원인을 방화벽 하나로 확정할 수 없다. [원본 시나리오](../src/test/resources/eval-dataset-v2.yml:1152)

이 과제의 판정은 두 형태로 분리할 수 있다.

| 형태 | 제공할 정보 | 요구할 결과 |
|---|---|---|
| 원인 미확정 | 현재의 오프셋·동기화·timeout 관측 | 동기화 이상과 관측 수치를 설명하고 방화벽·서버·경로 문제를 가설로 구분. 방화벽 확정은 인정하지 않음 |
| 원인 확인 가능 | 위 관측과 해당 대상·시각의 UDP 123 차단 근거 | 방화벽 차단과 동기화 실패의 관계를 설명. 특정 도구 순서는 강제하지 않음 |

둘 중 하나를 택해야 하는 문제가 아니라, 서로 다른 관측 조건을 가진 별도 과제로 유지할 수 있다는 제안이다. 정보가 추가되면 정당한 결론도 달라져야 한다. ‘방화벽이라고 답하는가’만 평가하는 정답표로 만들지 않는다.

MySQL replica 유무, Promtail 위치 파일 유실, GPU의 실제 서비스 영향도 같은 원칙으로 수정한다. 현재 38종별 조정 대상은 [비교 보고서](EVALUATION-RESEARCH-COMPARISON-2026-11-03.md)에 정리돼 있다.

## 5. 실제 구현 순서와 중단 조건

### 먼저 평가 환경을 검사한다

에이전트를 실행하기 전에 쿼리·대상·시간·오류 응답의 계약을 검사한다. 실제 도구와 다른 성공 응답을 주는 fixture는 수정한다. 제공된 도구로 과제를 풀 수 없는 필수 조건도 이 단계에서 보강·수정한다. 의도적으로 정보가 없는 과제는 정상적인 ‘확인 불가’ 과제로 명시한다.

이 검사를 통과하지 못한 사례를 모델의 실패로 집계하지 않는다. 유효하지 않은 사례 수와 이유를 별도로 공개한다.

### 그다음 판정기를 검사한다

정답 예시뿐 아니라 틀린 대상·틀린 단위·근거 없는 원인 확정·적절한 미확정·올바른 대체 경로를 포함하는 판정기 검증용 사례를 준비한다. 사람이 판정한 결과와 Judge 결과를 비교해 오판 유형을 확인한다. 판정기의 결과를 보고 같은 사례에 맞춰 프롬프트를 계속 고치면 평가의 독립성이 줄므로, 조정용 사례와 결과 보고용 사례를 구분한다.

임의의 새 가중치·합격 점수·데이터 분할 비율을 이 문서에서 정하지 않는다. 그런 숫자의 적절함을 뒷받침할 이 프로젝트의 측정 근거는 아직 없다.

### 마지막으로 v1·v2·v4를 동일 조건에서 다시 실행한다

- 같은 평가 버전·도구·상태·모델·생성 설정·실행 제한을 사용하고 매번 초기화한다.
- 평가 버전, 프롬프트 버전, 모델·백엔드, 시나리오 ID, 관측·도구 사건, 답변, 판정과 이유를 기록한다.
- 동일 과제를 반복한다. 기존 기본값은 3회지만 그것이 통계적으로 충분하다는 근거는 아니다. 반복 횟수는 실행 전에 정하고 기록한다. [현재 기본값](../src/test/java/io/ohgnoy/monitoring/eval/LiveEvalRunner.java:127)
- 실제 성공/실패, 판정 불가, 우발적인 실행 인프라 오류, Judge 파싱 실패를 구분한다. 의도적인 관측 서비스 장애는 인프라 실험 실패가 아니라 과제의 일부다.
- 비용·지연·반복 성공을 정답·정책 준수와 분리해 제시한다. 파싱 실패를 숨기거나 분모를 설명 없이 바꾸지 않는다.

새 환경에서 과거 답변만 다시 채점하는 것으로 실제 재실행을 대체하지 않는다. 도구 응답이 달라지면 에이전트의 후속 행동도 달라질 수 있기 때문이다. 과거 기록의 재채점은 판정기 점검용으로 구분한다.

## 6. 선택할 수 있는 범위

| 범위 | 측정할 수 있는 주장 | 제한 |
|---|---|---|
| 기존 요약 mock을 유지하고 정답·rubric만 보완 | 고정 관측 요약에 대한 답변 해석 품질 | 실제 조회 정확도·승인·복구를 입증하지 않음 |
| 도구 계약·상태 검증과 답변 의미 평가를 분리 | 도구를 사용하는 관제 에이전트의 과제 수행과 정책 준수 | 별도 환경·판정기 검증 필요 |
| 실제 장애 주입·복구까지 포함 | 통제된 환경의 실제 진단·복구 성공 | 운영 서버와 분리된 환경·실패 조건·복구 검증 필요 |

현재 요청에는 두 번째 범위를 권고한다. 근거는 사용자가 확인하려는 대상에 도구 사용·종료·사용자 질문 대응이 포함되기 때문이다. 이는 프로젝트 범위에 대한 설계 선택이며 논문이 이 구성을 유일한 답으로 증명했다는 뜻은 아니다. 실제 운영 서버에 장애를 주입할 필요는 없다.

38종의 권한 분포는 READ_ONLY 27개, NEEDS_APPROVAL 10개, NONE 1개이며 AUTO는 없다. 따라서 새 평가에서도 알람 분석·대화·승인 검사를 구분하고, 실제 복구 성공까지 주장하려는 경우에만 해당 검증을 추가한다.

## 7. 기존 포트폴리오 수치 처리

v1·v2를 포함한 과거 결과는 당시 데이터·모델·Judge·반복 조건의 실험 결과로 보존한다. 기존 기준에 한계가 있었다는 사실만으로 모든 숫자가 허위이거나 순위가 반대였다고 결론낼 수 없다.

다만 새 기준의 결과와 동일한 성능 지표처럼 비교하지 않는다. 새 결과가 나오기 전에는 ‘운영 정확도’ 대신 ‘자체 고정 관측·LLM 채점 조건에서의 결과’라는 범위를 명시한다.

이 개편의 첫 산출물은 높은 합격률이 아니라 **잘못된 조회와 관측 불가능한 정답을 구분하고, 타당한 대체 경로를 인정하는 평가 기준**이다. 이후 동일 기준의 재실행으로 v1·v2·v4를 비교한다.
