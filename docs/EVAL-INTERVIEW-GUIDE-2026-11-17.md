# 평가 개선 결정 기록과 면접 답변 가이드

기준일: 2026-11-17. 이 문서는 밤중 작업에서 최종적으로 채택한 결정과 그 이유를 정리한다. 이전 프로토콜의 모든 항목이 최종 기준인 것은 아니다. 숫자는 [최종 결과](EVAL-V5-VERIFIED-RESULTS-2026-11-17.md), 해석은 [신뢰성 결론](EVAL-V5-RELIABILITY-CONCLUSION-2026-11-17.md)을 우선한다.

## 먼저 기억할 결론

평가 코드를 실행하고 결과·검수·비용을 정리하는 작업은 완료했다. 그러나 **신뢰할 수 있는 최종 정확도와 하네스 순위라는 원래 목표에는 도달하지 못했다.** 추가 검증은 사용자의 요청으로 중단했다. 현재 성과는 출처·관측 근거·채점 실패를 추적할 수 있는 제한된 통제 평가와 개선 근거다.

### 면접에서 1분으로 설명하기

> 홈서버 관제 에이전트의 답변을 평가하면서, 처음에는 점수가 있어도 데이터셋의 출처와 채점기의 정확도를 충분히 설명하기 어렵다는 문제를 발견했습니다. 그래서 공식 운영 문서 기반의 통제 시나리오와 공개 장애 사례의 원리를 재현한 시험을 분리했습니다. 수치·단위·오차는 코드로 검사하고, 의미와 관측 근거는 별도 모델인 Haiku로 채점했습니다. 같은 답변을 두 번 채점하고 하네스 이름을 가린 독립 AI 검수도 추가했습니다. 같은 모델·도구·제약에서 실제 Pi와 간소화 하네스를 비교했지만, 반복별 순위 변화와 채점 무효가 있어 최종 우열을 주장하지 않았습니다. 대신 어떤 도구가 정보를 가리고 어떤 채점 기준이 불안정한지 구체적으로 확인했습니다.

## 면접 예상 질문과 답변

### 1. 데이터셋은 어디서 가져왔나요? 실제 장애 데이터인가요?

기존 공개 벤치마크를 그대로 사용한 것은 아니다. Google SRE의 진단 절차, Brendan Gregg의 USE Method, Prometheus·Docker 공식 문서 등을 근거로 홈서버에 맞는 통제 시나리오를 구성했다. 이런 자료는 **점검 절차와 지표 해석의 근거**이며 각 사건이 실제 발생했다는 증거는 아니다.

넓은 시험의 35문항은 매뉴얼 기반 통제 시나리오 30개, 공개 사례의 장애 유형을 적용한 2개, 비식별 운영 스냅샷 3개다. 별도 핵심 시험은 GitLab의 데이터베이스 장애 회고에서 다룬 pg_dump 버전 문제와 docker-library/postgres 이슈의 초기 SQL 접근 권한 문제를 격리 컨테이너에서 재현했다. 실제 사고 전체를 복제한 것은 아니고 버전·환경도 다르다. 정상·실패·복구·정보 부족을 포함한 8개 관측 조건도 독립적인 실제 장애 8건은 아니다.

확인: [출처와 통제 시험 설계](EVAL-V4-PROTOCOL.md), [재현 원리별 출처 매핑](../eval/v5/provenance.json). 이전 문서의 전체 사례 수와 최종 35문항 시험 수는 구분한다.

### 2. LLM Judge는 어떻게 구현했나요? Spring AI나 LangChain을 썼나요?

런타임 에이전트는 Spring AI를 사용한다. 이번 오프라인 평가 Judge는 별도 Python 실행 경로에서 Anthropic Messages API를 HTTP로 직접 호출한다. 코드의 모델 식별자는 `claude-haiku-5-5`다. LangChain을 사용하지 않았으며, 기존 런타임의 선택적 4차원 Judge와도 별개다.

직접 호출하는 작은 어댑터에서 구조화 출력, 응답 검증, 토큰 사용량·비용 기록, 실행 전 입력 고정과 예산 검사를 제어한다. 모델에게 100점 만점 총점을 임의로 매기게 하는 방식이 아니라, 요청한 항목별 판정과 근거를 받아 코드에서 집계한다.

확인: [HTTP 어댑터](../scripts/structured_haiku_v54.py), [공통 API·모델 설정](../scripts/haiku_rejudge.py), [최종 채점기](../scripts/score_legacy_eval_v55.py).

### 3. 무엇을 기준으로 정답을 판정하나요?

질문이 요청한 사실과 불확실성을 항목으로 나눈다. 수치 항목은 단위·차원·오차를 코드로 검사하고, Judge는 대상·시간 범위·의미·실제로 전달된 관측이 주장을 지지하는지 확인한다. 두 번의 유효한 채점이 모두 지지해야 항목 점수를 부여한다. 두 호출은 독립적인 진실의 보증이 아니라 같은 채점기의 반복 측정이다.

엄격한 질문 전체 통과는 모든 항목 정답, 요청한 형식 적합, 평가 가능한 무근거 주장 검사 통과, 실행 오류 없음까지 요구한다. 무효·불일치·실행 실패를 분모에서 빼지 않는다. 그래서 항목 점수와 질문 전체 성공률은 다르다.

### 4. 채점기가 정확하다는 것은 어떻게 확인했나요?

넓은 시험의 최종 채점 기준은 독립 AI가 만든 새 통제 문제 20개·21항목을 세 번 채점해, 최종 항목·전체 통과 판정 60회가 기대값과 일치하는지 확인했다. 보조 진단 라벨의 차이는 남겼다. 숫자·형식·예산·집계 로직은 별도 코드 테스트로 검사했다.

하지만 실제 답변에서는 420회 중 35회가 무효였다. 33회는 출력 토큰 한도, 2회는 필수 항목 집합 불일치였다. 통제 문제 통과가 실제 답변 길이·복잡도까지 보증하지 못한 것이다. 이 차이를 감추지 않고 다음 검증에 실제 크기의 관측 기록과 복합 항목을 포함해야 한다고 결론 냈다.

### 5. 독립 검수라면 사람에게 검증받았나요?

아니다. 첫 반복의 고정 70개 답변을 네 개의 별도 AI 컨텍스트에 나눠 답변당 두 검수자가 검토했다. 하네스 이름·자동 점수·상대 검수 결과는 제공하지 않았다. 원시 의미 항목은 156/162개, 고정 수치 검사를 결합한 판정은 161/162개가 일치했다.

수치 검사 코드는 공유하고 AI의 공통 오류 가능성도 남으므로 사람 검수나 완전히 독립적인 수치 검산이라고 말하면 안 된다. 검수자들이 명확하게 합의한 60개 답변 중 자동 채점과 일치한 것은 46개였고, 8개는 차이, 6개는 무효가 섞였다. 높은 검수자 간 일치율만으로 Judge 정확도를 인증할 수 없다.

### 6. Pi와 어떻게 공정하게 비교했나요?

실제 Pi와 애플리케이션의 간소화 하네스에 같은 모델·질문·시스템 프롬프트·도구·관측 환경을 제공했다. temperature 0, 응답당 출력 제한, 도구 호출 제한, 조사 시간 제한을 맞췄고, 실행 순서도 균형을 맞췄다. 각 문항을 양쪽에서 세 번 실행하고 모델 식별·입력·채점 코드의 해시를 기록했다. 채점에는 하네스 정체를 숨겼다.

다만 총 생성 토큰까지 같다고 주장하지 않으며, Pi 시작 시간도 제한에 포함된다. 이 결과는 통제된 조사·답변 능력 비교이고, 운영 전체 파이프라인이나 자율 복구 능력의 비교는 아니다.

### 7. 우리 하네스는 무엇을 단순화했나요? 왜 효과가 있다고 봤나요?

`FocusedInvestigator`는 공통 조사 프롬프트와 읽기 전용 도구를 한 대화 흐름에 연결하고 별도 reflection 초기화 없이 제한된 조사 루프를 실행하는 후보 구현이다. 공통 실행 계층에서 도구 호출·시간·관측 기록을 관리한다. 다단계 조사 비용을 줄일 수 있다는 가설을 시험했다.

넓은 시험에서는 실행시간 중앙값이 간소화 22.9초, Pi 36.0초였고 전달된 도구 응답 수 중앙값은 4개와 6개였다. 이는 이번 시험의 기술 통계다. 단순화의 각 요소를 따로 제거한 실험은 없으므로 어느 코드 변경이 정확도를 높였다고 인과적으로 단정하지 않는다. 운영 하네스를 교체해 성능 개선을 입증한 것도 아니다.

확인: [간소화 조사 구현](../src/main/java/io/ohgnoy/monitoring/application/agent/FocusedInvestigator.java), [공통 실행 계층](../src/main/java/io/ohgnoy/monitoring/application/agent/AgentExecution.java).

### 8. 최종 결과는 무엇인가요? 우리 것이 더 좋나요?

| 시험 | 우리 간소화 하네스 | Pi | 해석 |
|---|---:|---:|---|
| 35문항, 28계열 주 점수 | 61.8 | 53.6 | 계열별 동일 가중치의 잠정 자동 점수 |
| 같은 시험의 엄격 전체 통과 | 36/105 | 28/105 | 항목 점수와 다른 지표 |
| PostgreSQL 두 원리 재현 시험의 항목 점수 | 61.1% | 70.8% | 별도 8관측 조건, 합산 금지 |

넓은 시험의 주 점수는 문항별 반복 평균 → 계열 내 평균 → 28계열 동일 가중치 평균이다. 한 계열의 문항 수가 많다고 주 점수를 과도하게 지배하지 않도록 했다.

넓은 시험의 차이는 +8.23%p지만 반복별 차이는 -1.49, +17.26, +8.93%p로 방향이 바뀌었다. 선택한 계열 구성에 대한 민감도 구간도 [-4.86, +21.92]%p로 0을 포함한다. 채점 불일치·무효를 포함한 미해결 답변은 38/210개다. 사전에 정한 우열 조건을 충족하지 못했으므로 최종 승자를 정하지 않았다. 전체 홈서버 정확도의 신뢰구간이나 두 하네스의 동등성 증명도 아니다. 과거 76.7과는 기준이 달라 개선량을 계산하지 않는다.

### 9. 모델 문제 말고 도구 문제도 찾았나요?

구체적으로 두 가지를 확인했다. Loki 조회가 컨테이너 이름을 로그 라벨 대신 본문에서 검색해, 이름이 없는 YAML 오류 상세 줄을 놓친 사례가 있었다. 다른 원문 로그 도구로는 접근 가능했으므로 정보 자체의 부재와 조회 경로 선택을 구분했다.

또 누적 counter의 작은 증가를 상대 변화 10% 기준으로 요약하면서 “유지”로 표시한 사례가 있었다. 모델이 도구 요약을 따르면 증가를 놓칠 수 있다. 후속 개선안은 로그 선택 조건·문맥·잘림 여부를 명시하고, counter의 절대 증가·rate·reset을 분리해 전달하는 것이다. 이 개선안의 구현·재평가까지 완료한 것은 아니다.

확인: [실제 답변에서 확인한 도구 한계](EVAL-V5-OBSERVED-TOOL-LIMITS-2026-11-17.md), [추가 관측 도구 검토](EVAL-V5-TOOL-COVERAGE.md).

### 10. 비용은 얼마나 들었고 다음에는 무엇을 하나요?

넓은 비교는 35문항 × 2하네스 × 3반복 = 210답변, 답변당 두 번으로 420회 채점했다. 준비·실패한 검증·별도 핵심 시험까지 포함한 Anthropic API 비용 추정은 $1.1766077, 한도는 $2였다. 로컬 모델 GPU 비용·AI 검수 실행 비용·개발 시간을 포함한 프로젝트 총비용이 아니며 청구서 확정액도 아니다.

다음 작업은 실제 답변 크기를 반영한 Judge 출력 예산 검증, 복합 항목과 부가 오류의 적용 범위 명확화, 새 버전 고정 후 양쪽에 동일한 재평가 적용이다. 더 넓은 정확도를 말하려면 대표적인 실제 장애 사례, 별도 평가용 사례, 사람 검수 등 추가 증거도 필요하다. **추가 실행은 아직 하지 않았다.**
