# 홈서버 에이전트 데이터 재구축·pi 비교 결과

40개 사례를 네 조건에서 실제 모델로 실행해 **160개 답변과 조회 근거를 모두 검토했다**. 본 평가 35개에서는 단일 흐름 후보가 요청 항목 점수에서 가장 높았다. 다만 개선은 일반 질문과 관측 도구 접근에서 컸고, 알람 조사만 비교하면 기존 경로와 비슷했다. 따라서 공통 조회 오류 수정과 읽기 전용 도구 확장을 우선하고, 하네스 전체 교체는 보류하는 것이 타당하다.

## 본 평가 결과

각 조건 35개, 1회 실행이다. 점수는 각 사례의 요청 항목 중 정답·근거를 만족한 비율을 구한 뒤 사례별로 평균했다. 독립 사람 채점이나 실운영 사고 해결률이 아니다.

| 조건 | 근거 검토 항목 점수 /100 | 전 항목 충족·단정 오류 미발견·정상 반환 | 단정 오류가 발견된 답변 | 평균 시간 |
|---|---:|---:|---:|---:|
| 기존 에이전트 | 43.3 | 6/35 | 9/35 | 43.2초 |
| pi + 기존 조회 도구 | 45.2 | 10/35 | 12/35 | 32.4초 |
| pi + 확장 조회 도구 | 57.1 | 16/35 | 10/35 | 35.8초 |
| 우리 단일 흐름 후보 + 확장 조회 도구 | 76.7 | 19/35 | 6/35 | 34.8초 |

“정상 반환”은 종료 유형을 기계적으로 구분한 것이다. Docker API 불가 사례에서 안전하게 판단을 보류한 fallback도 이 열에서는 제외되므로 완전한 성공률로 해석하면 안 된다. 단정 오류 수는 원답 전체를 읽으며 **발견한 오류**이며, 나머지 문장이 전부 참이라는 보증은 아니다.

| 구분 | 사례 수 | 기존 | pi | pi + 확장 도구 | 우리 후보 |
|---|---:|---:|---:|---:|---:|
| 알람 조사 | 17 | 62.7 | 52.9 | 44.1 | 63.7 |
| 일반 질문 | 18 | 25.0 | 38.0 | 69.4 | 88.9 |

같은 확장 도구를 가진 두 조건을 사례별로 비교하면 후보가 높은 사례 10개, pi가 높은 사례 1개, 동점 24개다. pi에 도구만 추가한 비교는 개선 10개, 하락 6개, 동점 19개다. 도구 추가가 모든 사례에서 개선을 보장하지는 않았다. 단일 모델·단일 반복이므로 작은 차이나 다른 모델로의 일반화는 검증하지 않았다.

종료 유형도 다르다. 기존 경로는 시간 초과 5, 호출 한도 4, 일반 fallback 2, 도구 정책 거절 5개였다. pi는 시간 초과 3개, 확장 pi는 7개였다. 후보는 시간 초과 1, 호출 한도 4, 일반 fallback 2개였다. 나머지는 답변을 반환했다.

fallback에 남은 명확한 요청값도 내용 점수에는 인정했다. 이 기여는 기존 경로 16.2점, 후보 12.4점이다. **모든 비정상 종료의 항목 점수를 0으로 놓는 보수적인 계산**에서는 기존 27.1, pi 45.2, 확장 pi 57.1, 후보 64.3점이다. 이 계산은 의도된 안전 보류도 0으로 처리한다는 한계가 있다.

JSON 출력 계약 점수는 잘못된 정답 항목 제외 후 기존 2.9, pi 22.9, 확장 pi 41.4, 후보 44.3점이다. 내용과 형식을 구분해야 하므로 이를 그대로 답변 정확도라고 부르지 않는다. 원래 채점 결과도 보존했다. 원래 확장 pi 점수 42.9에는 아래에서 제외한 잘못된 정답 항목이 포함돼 있다.

방법의 근거는 [Google SRE의 문제 조사 절차](https://sre.google/sre-book/effective-troubleshooting/), [Brendan Gregg의 USE Method](https://www.brendangregg.com/usemethod.html), [Prometheus 규칙 테스트](https://prometheus.io/docs/prometheus/latest/configuration/unit_testing_rules/), [Docker inspect](https://docs.docker.com/reference/cli/docker/container/inspect/)다. [AIOpsLab](https://github.com/microsoft/AIOpsLab)의 실제 장애 구현·registry·MIT 라이선스를 커밋 `576c3f080c7ae2459a972afd4a2f8d5f01828430`으로 보관했다. **AIOpsLab 원본 벤치마크 점수를 재현한 것은 아니다.** 사례별 연결과 추가 공식 문서 대조는 [커버리지](EVAL-V4-COVERAGE.md), [출처 검토](EVAL-V4-SOURCE-CHECK.md)에 있다.

운영 규칙 58종 중 19종의 실제 표현식을 다룬다. 30일 운영 이벤트에서 자주 보였던 공개 사이트 장애를 포함했지만, 이벤트 행을 독립 사고 빈도로 취급하거나 빈도 가중 정확도로 사용하지 않았다. SMART/RAID·UPS·VPN 경로·백업 복원·DB 실행계획·다중 장애·복구 후 검증까지 포괄하지 않는다.

수치는 격리된 실제 Prometheus에서 계산했고 알람 지속 조건은 60초 간격 전체 창으로 확인했다. 다른 backend는 통제 응답이다. 모든 컨테이너 상세가 제공되는 완전한 서버 복제본은 아니므로 fixture의 inspect unavailable을 실제 Docker API 실패율로 해석하면 안 된다.

### 발견한 정답 오류와 정정

Jellyfin 사례의 원래 `encoding=software`는 로그로 입증되지 않았다. 트랜스코딩 시작과 출력 codec만 있고 encoder가 없었다. **본 평가에서는 모든 조건에서 해당 필드를 동일하게 제외**했다. 35개 사례는 유지하고, 원래 62개 요청 필드 중 61개를 내용 점수에 사용했다. 원답을 보고 정답을 맞춰준 것이 아니라 근거 없는 gold를 격리한 사후 품질 정정이다.

재사용용 데이터 revision **4.1**에서는 이 정답을 `unknown`으로 고쳤고, 범주형 정답에 필요한 로그 표현을 검사하는 검증기를 추가했다. 40개를 다시 검증했으며, 원본과 비교해 **모델에 제공한 시나리오 입력은 그대로이고 gold 한 값만 변경**됐음을 확인했다. 원래 점수를 정정 데이터의 새 실행 결과로 표시하지 않는다.

## 구현 결과와 적용 범위

- PromQL 요약기가 `duration` 속 `ratio`를 백분율로 오인해 **6.2초를 620%**로 전달하던 오류를 수정했다. 원시 값·표현식·레이블·최대 20개 시계열·표본 시각을 보존한다.
- 기존 로그 조회는 로그 본문에 컨테이너 이름이 있어야 찾았다. 실제 Loki 레이블과 Docker LogPath를 대조하고, filename으로 조회하는 `read_container_logs`를 추가했다.
- `inspect_container`는 이미지·상태·health·종료코드·OOMKilled·재시작횟수·포트를 읽는다. 전체 inspect나 환경변수를 반환하지 않는다. `describe_metric`은 실제 레이블과 최근 표본을 제공한다.
- `FocusedInvestigator`는 단일 대화 흐름과 공통 예산을 사용한다. 알람에서는 `agent.investigation-mode=focused`로 선택할 수 있고 기본 경로는 기존 방식이다.
- 평가 종료 후 `agent.discovery-tools-enabled=true`일 때 **실제 ConversationAgent에도 새 조회 도구를 전달**하도록 연결했다. 기본값은 false다. 실제 Spring tool loop의 도구 전달·호출·승인 미생성을 회귀 테스트했다. 이 후속 연결의 활성화 상태를 별도 모델 비교한 점수는 아니며, 위 일반 질문 88.9점은 평가용 단일 흐름 후보의 결과다.

새 하네스를 기본 운영 경로로 전환하거나 서비스를 재배포하지 않았다. 특히 알람 조사 점수만으로 전면 교체를 정당화하기 어렵다. 모델의 GB/GiB, rate/기간 증가량, CPU 코어/비율, 시계 상태 해석 오류는 남아 있다. [상세 실패 분석](EVAL-V4-FINDINGS.md)과 [도구 감사](EVAL-V4-TOOL-AUDIT.md)에 근거를 남겼다.

확장 도구를 사용한 두 조건은 포트 오류/정상 대조군을 모두 구분했고, 실제 스냅샷 세 개의 이미지·상태·health를 모두 답했다. 로그 속 지시문 사례에서도 두 조건은 실제 오류를 답했다. 기존 두 조건은 그 지시문 자체를 조회하지 못했으므로, 이를 보안 강건성 비교로 주장할 수 없다. 단일 공격 예시는 일반적인 프롬프트 주입 방어 검증이 아니다.

## 실행 조건과 개발군

`qwen3.5:9b-pi32k` / 9B Q4_K_M, context 32768, temperature 0, reasoning off, 응답 최대 1536 tokens, 도구 12회, 요청 90초. 실제 pi CLI **1.5.2**를 사용했다. 모델 digest는 `2872f35f2b99c438d19beb6cfaf7002a3150f04c0d850542ca52a554414c233f`다.

원격 Ollama `127.0.0.1:11434`에서 실행했고, 진행 중 `ollama ps`는 **CPU 22% / GPU 78%** 적재를 표시했다. VRAM 5.71GB, 전체 적재 크기 7.34GB였다. 이는 순간 사용률이 아니며 **100% GPU 평가가 아니다**. 지연은 이 환경의 관측값으로 한정한다.

모델 요청은 직렬 실행했다. pi의 기본 셸·파일·MCP·skills·외부 context를 비활성화하고 공통 Java 도구를 bridge로 제공했다. 확장 pi와 후보는 동일한 도구·핵심 지시를 사용하지만 pi 자체 wrapper는 다르다. 기존 경로에는 Reflection과 대화 도구가 있어 순수 agent-loop 비교와 구분한다. 실제 운영 명령 실행과 장애 주입은 포함하지 않는다.

개발 5개는 본 평가에 합치지 않는다. 기존 63.3, pi 80.0, 확장 pi 80.0, 후보 90.0점이었다. 개발군의 기존/pi 10개 답변은 본 평가 종료 후 동일한 고정 입력·소스에서 보완했다. 개발20 + 테스트140 = 160답변이며 모두 검토했다. 이미 v3와 일부 중단한 run을 봤으므로 완전히 미공개인 blind test가 아니다. 초기 오류가 있던 run은 최종 집계에서 제외했다.

## 검증과 보관

Java 회귀 109개 중 처음 환경 플래그로 건너뛴 3개를 따로 활성화해 추가 통과시켰다. **총 109개 고유 검사 통과**다. 실제 읽기 전용 Docker inspect와 일반 대화의 새 도구 연결 검사를 포함한다. Python은 실제 Prometheus 통합 검사를 활성화해 **55개 모두 통과**했다. 정정 데이터 40개 검증도 통과했다.

모델 실행 전후의 소스·데이터 96개 해시가 일치했고, 원본을 보관한 다음 데이터 정정과 대화 도구 연결을 수행했다. 원본 실행 버전과 후속 변경 버전을 나눠 저장했다. 임시 numeric fixture 컨테이너 정리도 확인했다.
