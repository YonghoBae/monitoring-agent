# 원답 검토에서 확인한 실패와 개선 범위

이 문서는 `campaign-20261116-203700`의 답변과 관측을 대조한 사례 분석이다. 전체 점수는 최종 결과 보고서를 따른다. 조건별 원답과 인용은 각 run의 `answer-review.json`에 있다. 독립 사람 검토는 수행하지 않았다.

| 관찰 | 사례의 실제 근거 | 의미 |
|---|---|---|
| 잘못된 단위가 자연어와 JSON에 함께 들어간다 | 디스크 여유 8×10⁹ bytes를 1024³으로 나눈 뒤 7.45 **GB**라고 답함. 별도 답변은 올바르게 GiB라고 표시함 | 원시 값 전달을 고친 뒤에도 모델의 단위 변환은 별도 실패 지점이다. GB/GiB 표기가 명확한 동일 물리량만 정규화했고, 잘못 붙인 단위는 고쳐 채점하지 않았다. |
| counter의 rate와 증가량을 혼동한다 | 15분 알림 실패 증가량은 4인데 초당 rate 약 0.0044를 실패 횟수로 제출 | 숫자 추출만으로 채점하지 말고 요청 기간·집계·단위를 묶어야 한다. 채점기가 모델 대신 rate×900을 계산하면 실패를 숨기게 된다. |
| 잘못된 레이블로 빈 결과를 얻은 뒤 수집 문제를 추측한다 | 실제 레이블은 `name="jellyfin"`인데 `container="jellyfin"`으로 조회 | `describe_metric`과 시계열 레이블 반환은 필요하지만 사용을 보장하지는 않는다. 빈 결과와 실제 관측 장애를 구별해야 한다. |
| 정답 숫자가 있어도 설명이 틀릴 수 있다 | GPU VRAM 23859 MiB와 연산 사용률 45%를 맞힌 뒤, 메모리 알람 조건이 충족되지 않았다고 단정 | 요청 필드 점수와 과잉 단정 검토를 분리해야 한다. VRAM 점유율 약 97%와 연산 사용률은 다른 지표다. |
| 관련 로그를 읽었다는 사실만으로 원인이 입증되지는 않는다 | Alertmanager의 일반 설정 로딩 실패 줄만 읽고 YAML 파싱 오류로 확정 | 실제 `yaml: line 42` 줄까지 조회한 조건과 구분했다. 도구 이름 기반 자동 근거 점수의 한계다. |
| 같은 추가 도구가 있어도 필요한 것을 사용하지 않을 수 있다 | 확장 pi는 Alertmanager에서 기존 본문 검색을 선택했고 compact는 filename 조회로 오류 줄까지 읽음 | pi_plus/compact_plus 차이는 같은 도구의 선택·종료 방식 비교다. 도구 보유와 근거 도달은 별도다. |
| 조사를 넓히다가 이미 답할 수 있는 항목까지 미완료로 끝난다 | OOM 사례에서 전체 컨테이너 inspect를 순회하다 시간/호출 한도 소진 | 필요 관측을 우선하고 자료가 없는 원인은 unknown으로 종료하는 정책이 필요하다. fixture 상세 미제공은 실제 Docker 실패율이 아니다. |
| 검증기가 통과한 데이터에도 의미 오류가 남을 수 있다 | Jellyfin 로그에는 encoder가 없지만 원래 gold는 software | 수치 재생과 로그 존재 검증만으로 충분하지 않다. 이 필드는 모든 조건의 내용 점수에서 제외하고 원본과 정정 이유를 보존했다. |

이번 코드 수정은 공통 PromQL 요약기의 잘못된 자동 단위 변환 제거, 레이블·다중 시계열 보존, 선택 필드 Docker inspect, filename 기반 로그 조회, 단일 대화 흐름의 선택형 조사 하네스다. 마지막 항목이 항상 더 정확하다는 전제는 두지 않는다. 운영 기본 경로를 교체할 판단은 완료율·근거 없는 단정까지 포함해야 한다.

다음 개선은 단순 프롬프트 강화보다 관측 계약이 먼저다. 값과 단위를 분리하고, 기간 증가량과 초당 rate를 구별한 조회 결과, 알려진 메트릭의 실제 레이블 탐색, 핵심 근거 누락 시 종료 사유를 구조화할 필요가 있다. kernel/journal·compose 관계·DB 실행계획·백업 복원처럼 현재 관측에 없는 정보는 새로운 데이터가 필요하다. 최종 테스트를 보고 같은 입력에서 지시문을 반복 조정해 점수를 올리는 작업은 하지 않았다.
