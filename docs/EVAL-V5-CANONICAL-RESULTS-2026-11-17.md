## 실제로 드러난 실패

- 임시 PostgreSQL 시작 메시지를 전체 초기화 성공으로 해석하고, 뒤의 초기 SQL 접근 거부를 놓치는 답변이 있었다.
- 복원 검사 결과가 실제 도구 응답에 있는데도 확인할 수 없다고 답한 사례가 있었다.
- 제한시간 내에 근거를 조회하고도 요청한 결론을 정리하지 못한 답변이 있었다.

따라서 조회 도구 추가만으로 모든 문제가 해결된다고 볼 수 없다. 이미 전달된 근거를 구분하고, 제한 안에서 결론을 완성하는 능력도 중요하다. 실행시간 중앙값은 Pi32.0초, 간소화 하네스40.1초였고, 전달된 도구 응답 수 중앙값은 모두4개였다. 이 수에는 캐시 응답도 포함되며, 전체 추론 토큰 수가 같다는 뜻은 아니다.

## 출처와 한계

- 공개 사례의 구버전 pg_dump/신버전 PostgreSQL 불일치와 초기 SQL 접근 거부를 격리 컨테이너에서 정상·장애·복구 조건으로 실행했다. 원래 서버 사건 전체를 그대로 재생한 것은 아니다.
- 부분 관측 조건은 원인이나 후속 확인 결과를 숨겨, 모르는 것을 단정하지 않는지 검사한다. 일반 컨테이너 종료 코드만으로 특정 초기화 단계의 실패를 확정하지 않는다.
- 복원 표본 확인은 전체 백업 무결성이나 운영 복구 완료의 증명이 아니다. 초기화 복구는 새 데이터 디렉터리에서 재시도했다.
- 실제 장애 복구는 재현 스크립트가 수행했다. 이 비교는 에이전트의 조사·답변 능력 평가다.
- 기존76.7이나 앞선 탐색 비교와는 요청 항목 공개 방식·측정 범위가 달라 성능 향상/하락량으로 직접 계산하지 않는다.
- 고정한 정답의 설명에는 앞선 두 JSON키 요청을 가리키는 역사적 문구가 남아 있다. 이 시험의 실제 모델 요청과 필수 의미 항목은 모두3개이며, JSON키 형식은 핵심 시험의 점수 조건이 아니다. 원본을 수정하지 않고 이 설명상 한계를 기록한다.
