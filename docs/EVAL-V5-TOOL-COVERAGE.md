# Live observation coverage versus v5 replay

Reviewed 2026-11-17 by an independent AI reviewer using repository code and the existing v4 audit. No deployment, new collector, live production probe, or external-source search was performed for this document. This is a code-and-artifact audit; current production enablement and collector health were not reverified.

**v5 proves that two PostgreSQL failure mechanisms produced the captured outcomes. It does not prove that the current production monitoring stack collects or exposes every observation used in the replay.** The builder aggregates real `pg_dump`/`psql` subprocess output, Docker state and Docker log output into collector-like log records. Those wrappers are evaluation adaptations. A correct replay answer demonstrates interpretation of delivered evidence, not successful live discovery of the same evidence.

## What the current interfaces can observe

The relevant source is `ObservationDiscoveryTools.java`, `AgentTools.java`, `CommandExecutorService.java`, `LokiQueryService.java` and `PrometheusQueryService.java`. Paths are under `src/main/java/io/ohgnoy/monitoring/`. `AgentToolsFactory.createDiscoveryTools()` explicitly describes the enhanced discovery surface as optional and not enabled by default. Availability in the enhanced comparison is not evidence of production deployment.

| Interface | Supported observation, when available | Boundary that matters for diagnosis |
| --- | --- | --- |
| `read_container_logs(name, minutes)` | Uses Docker's current `.LogPath` for the named container, then queries Loki with the exact `job="docker", filename=...` selector. It can target a known stopped container that still exists. | Reads already-ingested Loki records; it neither executes diagnostic commands nor creates a backup-job collector. Requires Docker access, a usable local log path, matching Loki labels, retained records and a known exact name. A deleted container or unavailable log path defeats this lookup even if some historical log data may exist elsewhere. |
| `inspect_container(name)` | Selected current fields: name, configured image reference, status, OOMKilled, exitCode, restartCount, configured health status and port mappings. | No host file owner/mode/ACL, effective process identity, mounts, network attachments/aliases, Compose dependencies, resource limits, complete state history or SQL results. The image reference is not a measured pg_dump/client/server version. `exitCode` is container state, not necessarily a backup subprocess's exit code. `health=not_configured` is not a passed health check. |
| `query_prometheus` (the general metric-query tool), `list_metrics`, `describe_metric` | Queries existing Prometheus data; metric discovery and recent label/sample summaries help select the intended entity. Range summaries preserve expression, raw magnitude, labels, sample time and finite sample count, for up to 20 series. | Can report backup timestamps, exits, versions or restore checks only if suitable metrics actually exist and encode those facts. No exporter or SQL/file probe is created by asking a query. Summaries are not raw event history or proof of causation. A filtered name list is not the complete metric catalog. |
| `get_containers` | Names returned by `docker ps`, cached for that tool instance. | Running inventory only. A missing name does not prove a service never existed or that a job succeeded. It does not discover stopped/deleted jobs. |
| Legacy `query_loki` | Searches `{job="docker"}` for the requested container name in log text. | Can miss real application logs whose body lacks that name. It is not equivalent to the filename-based enhanced tool. |
| `search_rag` | Retrieves stored prior cases or notes. | A prior incident is a hypothesis source, not evidence that the same cause or remedy applies now. It cannot replace missing current observations. |

The live log service requests at most 30 records, newest first from Loki, then displays them chronologically; each line is shortened to 300 characters. There is no pagination or separate full-record fetch in these interfaces. A crucial error can therefore fall outside the selected records or beyond the displayed prefix. v5 includes long one-line JSON command wrappers and 55–79-line initialization views; availability of the original capture file does not mean a model received all its contents. Score against actual delivered tool envelopes, including truncation and caching, not the full replay world.

Docker inspection has a five-second timeout and a 64 KiB output bound. Invalid names, inaccessible Docker, absent containers, empty/nonlocal log paths and backend failures are observation failures, not normal service states. Loki and Prometheus errors are thrown rather than deliberately converted into empty successful results, but the runner must preserve that distinction. An empty Loki result can still mean no matching retained records, wrong identity/time window or collection gaps. It cannot establish “no errors occurred.” A missing metric, nonfinite sample or restricted/partial result likewise cannot establish zero or health.

## v5 evidence that is supplied by replay

| Fact used or discussed in v5 | Actual capture origin | What the live surface can establish today |
| --- | --- | --- |
| pg_dump failed with an explicit version mismatch | Capture event 24: stdout/stderr and exit code from a foreground Docker command invoking pg_dump | The direct cause is observable only if that specific diagnostic reaches Loki or another accessible job record. The server container's ordinary logs and current state are not a substitute for the client result. |
| Client 16.16 and server 17.12 | Event 23 invokes `pg_dump --version`; event 18 invokes `psql` with `SHOW server_version`; event 24 also embeds both versions in the diagnostic | Current selected inspect fields cannot measure either executable version. The diagnostic, if collected intact, suffices for this failure; image tags alone do not independently verify runtime versions. |
| Successful baseline/recovered dump | Events 19/25 capture dump output and command exit code | Current tools have no dedicated successful-backup run record. A running database or absence of error logs does not establish a completed backup. The `--rm` client containers are removed, so later current-name inspection is insufficient. |
| Restored marker count 3 and sum 60 | Events 22/28 capture `psql` output from a check of separately restored test databases | No current tool runs this SQL or reads a dedicated restoration report. The script captures `docker exec` output directly; no reviewed implementation forwards that result into the server's Loki stream. These values are replay-supplied, optional unscored facts. |
| Initialization failed and named SQL was unreadable | Event 51 inspects the failed container; event 52 reads Docker logs | This is the closest match to existing enhanced tools: preserved container state plus retained logs could support the immediate permission error. It still depends on actual collector/index/retention availability. |
| Initialization completed and marker count is 3 | Events 43/67 contain initialization/startup logs; events 42/66 separately capture SQL query output | Logs may support completed initialization/startup. They do not automatically expose the separate marker query. A ready message is not full application health or restored production data. |
| Host SQL UID/GID 1000, mode 0600, then chmod intervention | Python filesystem inspection and mutation recorded in phases/script | Not available from the current selected inspect/log/metric interfaces. The replay correctly excludes this collector metadata from agent views. The error alone cannot uniquely identify DAC owner/mode versus every other access-control explanation. |
| Fresh PGDATA was used for the recovered initialization | Reproduction script creates a new disposable container/tmpfs; phase provenance records the intervention | A successful view alone cannot reveal the earlier failure or prove in-place repair. The gold limits the claim to the captured successful operation. Production state inspection does not supply this experiment history. |

The current replay contains no metric series, and its `service-db` identity merges command results into one convenient evidence stream. In production, a backup scheduler/client and database server may have separate identities, permissions, clocks and retention. A future collector must preserve their relationships explicitly rather than rely on the replay alias. An OOMKilled flag or restart count is also a different quantity from job failure history; neither supplies a missing pg_dump exit status.

## Prioritized read-only observation additions

These are proposals, not implemented or deployed changes. The first priority is reliable collection and explicit observation status; adding more model instructions cannot recover absent data.

| Priority | Proposed collector/tool capability | Why it closes a real gap; limits to preserve |
| --- | --- | --- |
| 1 | Structured backup-job records and a bounded reader keyed by job/run ID | Persist start/end time, target identifier, command/tool version, measured server version when known, exit status, sanitized diagnostic, artifact identifier and last-success history. Retain short-lived/deleted job identity. Distinguish “backup produced” from “restore verified”; omit credentials and dump contents from ordinary diagnostic records. |
| 1 | Log-result metadata plus bounded pagination/full-event retrieval | Return requested interval/selector, backend status, count, truncation, earliest/latest timestamps and stable event IDs. Preserve a path to the full decisive error within fixed budgets. Expose collector freshness separately from “zero matching records.” |
| 1 | Read-only restoration-report retrieval | Read timestamped results from a separately authorized isolated restore-validation job, bound to the exact backup artifact, checks and target environment. The diagnostic tool should not silently perform restore writes. Report tested scope; a three-row/count-sum check cannot certify an entire production backup. |
| 2 | Container/job history and narrow dependency inspection | Retain lifecycle/exit/OOM events and stable identities after removal; expose selected mount, network/alias, resource-limit and Compose dependency metadata. Keep current snapshot versus historical event distinctions, source timestamps and explicit unavailable states. |
| 2 | Allowlisted file-access metadata inspection | For known configuration/init paths, report numeric UID/GID, mode, relevant ACL/access-policy availability and the intended container user/mount context. Avoid unrestricted shell/file reads. When no direct access test exists, distinguish metadata-based hypotheses from demonstrated readability by that process. |
| 2 | Bounded host kernel/systemd event reader | Make OOM victim/cgroup and failed-unit evidence reachable, with timestamps and retention/access limitations. Correlate with container identity instead of assigning a victim from an OOM counter alone. |
| 3 | Explicit DNS/TLS/connectivity probes and topology observations | Add target-scoped, timestamped results that distinguish resolution, connection, TLS and HTTP stages and state where the probe ran. A single probe result cannot explain every router/VPN/upstream failure. |
| 3 | Storage, GPU and deeper database diagnostic readers | Read already-collected SMART/RAID/UPS, per-process/cgroup usage, GPU process/device evidence and bounded DB lock/query-plan observations where authorized. Require evidence for the specific diagnosis; do not infer physical disk faults, driver failures or missing indexes from utilization/latency alone. |

## Existing regression breadth versus new mechanism proof

The [v4 coverage document](EVAL-V4-COVERAGE.md) describes 40 controlled cases, including 35 test cases, with 19 of 58 operational rule expressions exercised. The [v4 source check](EVAL-V4-SOURCE-CHECK.md) explicitly separates source-informed fixtures from original incident evidence. The [v4 tool audit](EVAL-V4-TOOL-AUDIT.md) records the observation gaps that remain relevant here. These provide useful regression coverage, not an empirical incident-accuracy denominator.

| Area | Existing v4 regression coverage | New v5 mechanism evidence | Next independent family/evidence needed |
| --- | --- | --- | --- |
| Backup/database initialization | Backup delay/failure timestamps, exit fixtures, slow-query/lock examples | Actual incompatible-client failure and unreadable initialization SQL, with bounded normal/fault/recovered captures | A distinct backup artifact/restore-integrity or scheduler failure with original run records, a specific intervention and independent recovery checks |
| Network/HTTP/DNS/TLS | HTTP down/slow/recovered, DNS-stage latency, certificate expiry/renewal logs, SSH probes, target-port adaptation | None | Source-backed connectivity or renewal incident with endpoint/topology/phase evidence and a verified repair; Compose 12593 remains rejected as a clean unique-cause source |
| Disk/storage | Filesystem capacity and I/O metric fixtures | None | Separate space/inode versus physical-device/storage-path fault cases, with direct evidence and bounded post-repair verification |
| Container restart/OOM/systemd | Restart/startup and host-OOM controls, failed-unit examples, selected Docker snapshots | Initialization exit only; no cgroup/host-OOM mechanism proof | Independent cgroup-limited OOM versus host OOM, preserved victim/lifecycle history and post-recovery service checks |
| CPU/RAM/GPU/transcoding | Resource metrics, GPU temperature/VRAM, encoding-log controls | None | Distinct CPU/process saturation, GPU memory/driver or workload-configuration incidents with device/process evidence and verified outcomes |
| Time/configuration/notifications | Clock synchronization, parser/reload, bind/environment and delivery-failure controls | None | Independent source-backed configuration or delivery incident with original diagnostic and recovery evidence |
| Missing/restricted observations | Unknown metric, inventory unavailable, partial recovery and log-instruction controls | Two deliberately detail-withheld views require an unknown cause despite known failure | Genuine collection failure, retention/truncation and permission-denied cases, keeping unknown, unavailable and healthy outcomes distinct |

Two PostgreSQL mechanisms cannot cover network, disk, OOM, certificate, GPU or other recurring homelab problems. Eight phase/detail views and repeated agent executions do not increase the number of independent incident families. Historical alert counts are not verified independent root-cause frequencies. Future selection should use independently sourced incidents with preserved normal/fault/recovery evidence and reachable discriminating observations; it should not obtain apparent breadth by merely relabelling the same fixture or adding more phase variants.

Report v4 regression behavior, v5 mechanism-backed replay behavior and future live collector validation separately. For every failure, distinguish missing source data, inaccessible tools, lossy summaries, failure to query, misinterpretation and output-contract errors. That makes the comparison useful without attributing an observability gap to model reasoning or treating replay success as deployed operational competence.
