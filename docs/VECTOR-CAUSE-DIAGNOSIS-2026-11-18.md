# 검색 정확도 원인 진단 — 2026-11-18

**어제 모든 개선 방법을 시험한 것은 아니다. 모델·리랭커 비교는 했지만, 검색에 필요한 정보가 충분한지 확인하는 실험이 빠졌다.** 이번에는 이전 최종 결과를 유지한 채, 같은 질문·정답·후보를 사용해 입력과 검색 조건을 하나씩 바꿨다.

현재 가장 분명한 관찰은 **제목만 검색어로 사용한 정보 손실과, 큰 후보 풀에서의 경쟁**이다. 새 모델만으로 해결되지 않았고, 문서 길이·청킹이 주원인이라는 가설도 제한된 대조에서 강하게 지지되지 않았다. 데이터 전체가 잘못됐다고 결론낼 근거도 없다.

이 결과는 이미 시험한 영어 질문 91개를 다시 사용한 **사후 원인 진단**이다. 독립적인 새 시험 점수나 검증된 운영 개선으로 제시하지 않는다. 한국어 원문 운영 기록, 리랭커에 본문을 넣는 조건, 생성 답변의 정확도는 이번 추가 진단 범위에 없다.

## 어제 한 것과 하지 않은 것

| 항목 | 실제 실행 범위 |

| 입력 형식 | E5 query/passage와 query/query 비교 |

| 운영 적용 | 배포·인덱스 변경·실제 API 전체 지연 검증은 하지 않음 |

원본 [계획](../eval/vector-v3-improvement/protocol.json)과 [변경 기록](../eval/vector-v3-improvement/development-amendments.json)이 근거다. 앞선 “13개 조건 완료”는 그 조건들의 실행 완료를 뜻하며 가능한 원인을 모두 확인했다는 뜻으로 전달하면 안 됐다.

## 1. 질문 정보 부족: 두 임베딩에서 개선 확인

문서 48,235개와 기존 문서 벡터·정답 ID를 유지했다. 질문 제목에 **그 질문의 본문**만 추가했다. 정답 문서나 답변 본문을 검색어에 넣지 않았다. 두 모델에 같은 입력 문자열을 제공했지만 토크나이저가 달라 유지되는 글자 범위까지 같지는 않다.

| 방법 | 검색어 | nDCG@10 | Hit@5 |
|---|---|---:|---:|
| 기존 MiniLM | 제목 | 0.3056 | 33/91 |
| 기존 MiniLM | 제목 + 질문 본문, native 256토큰 | **0.4018** | **44/91** |
| Qwen | 제목 | 0.2337 | 28/91 |
| Qwen | 제목 + 질문 본문, 256토큰 | **0.3717** | **43/91** |
| Qwen | 같은 본문, 512토큰 | 0.3979 | 47/91 |

제목→본문 추가의 nDCG 차이 95% paired cluster 구간은 MiniLM **+0.0962 [0.0340, 0.1657]**, Qwen **+0.1380 [0.0789, 0.1989]**다. 80개 공유 정답 묶음에서 2,000회 계산했다. 사후 여러 비교 중 얻은 설명적 구간이며 다중 비교 보정이나 독립 확인 시험은 아니다.

Qwen은 Hit@5가 좋아진 질문 21개, 나빠진 질문 6개였다. MiniLM은 각각 18개와 7개다. 본문을 무조건 길게 넣으면 모든 질문이 좋아진다는 결과가 아니다. Qwen 512와 MiniLM 본문 조건의 nDCG 차이는 −0.0039, 구간 [−0.0809, +0.0680]으로 Qwen 우위를 입증하지 못했다.

고정된 성공·실패 표본 12개를 읽었을 때, 한 질문의 제목은 단순한 업데이트 문제였지만 본문에는 PPA의 Release 파일 부재가 적혀 있었다. 다른 질문은 deb 설치라는 제목 뒤에 apt 저장소 목록 구문 오류가 있었다. 제목만으로는 구체적 증상과 목적이 빠지는 사례다. 성공 표본 중에는 본문 없이도 해당 정답을 찾은 경우도 있어 모든 실패를 이 원인으로 설명하지 않는다.

**누출 점검:** 질문 본문에서 대상 사이트 질문 URL을 제거하는 동일 규칙을 적용했지만 실제 제거 건수는 0, 정답 숫자 ID 포함도 0이었다. 정답 제목과 같은 문자열은 4개에서 발견됐다. 일부는 일반적인 apt 오류 문구라 이것만으로 누출이라고 판정할 수 없다. 보수적으로 4개를 제외한 87개에서도 MiniLM Hit@5는 **30→42**, Qwen 256은 **25→40**, Qwen 512는 **25→44**였다. 다만 수집 당시 본문에는 편집·사후 해결 단서가 있을 수 있고 질문 작성 당시의 revision을 복원하지 않았으므로 실시간 장애 입력과 같다고 주장하지 않는다.

## 2. 후보 문서 규모: 동일 질문에서도 큰 영향

같은 질문 91개와 벡터를 유지하고, 모든 알려진 정답을 포함한 5,000개 후보를 ID 해시로 고정했다. 전체 48,235개와 비교했다.

| 제목 입력 고정 | 문서 5,000개 | 문서 48,235개 |
|---|---:|---:|
| MiniLM nDCG@10 / Hit@5 | 0.4843 / 52/91 | 0.3056 / 33/91 |
| Qwen nDCG@10 / Hit@5 | 0.4333 / 49/91 | 0.2337 / 28/91 |

후보 수를 늘리면 비슷하지만 정답표에는 없는 문서들이 정답보다 앞에 온다. 작은 합성 자료의 높은 점수가 큰 검색 공간에서 유지되지 않은 이유 중 하나로 후보 경쟁을 확인했다. **정답을 알고 보존한 축소 풀**이므로 52/91을 새 서비스 성능으로 제시하거나 문서를 임의로 버리는 개선을 권하지 않는다. 관련성 미판정 문서도 있어 늘어난 후보를 모두 진짜 오답이라고 단정할 수 없다.

## 3. 문서 잘림·청킹: 이번 대조에서는 작은 변화

Qwen 기준 정답 연결 109개 중 33개는 정답 문서가 256토큰보다 길었다. 모든 질문 제목은 256토큰 안에 들어갔고, 제목+본문은 91개 중 42개가 256토큰, 16개가 512토큰을 넘었다. 질문 정보 누락과 문서 잘림을 구분했다.

사전에 ID 해시로 고른 영어 질문 32개에서 정답과 원래 네 방법의 상위 3개 결과를 합친 **동일 후보 집합**을 만들었다. 고유 문서는 284개다. 문서 전체를 256토큰·64토큰 겹침으로 나누면 607개 조각이었다. 질문 벡터는 제목 조건 그대로 유지했다.

| 문서 표현 | 정답 1위 | 후보 집합 내 nDCG@10 |
|---|---:|---:|
| 원래 앞 256토큰 | 4/32 | 0.3782 |
| 새로 계산한 같은 앞 256토큰 | 4/32 | 0.3782 |
| 문서 제목만 | 5/32 | 0.4128 |
| 앞 512토큰 | 4/32 | 0.3809 |
| 전체 조각의 최대 유사도 | 4/32 | 0.3804 |

전체 조각 방식은 정답 순위가 3개 질문에서 개선되고 나머지는 같았지만 1위 회복은 없었다. 문서 앞부분만 읽은 것이 주원인이라면 크게 개선될 것이라는 가설은 이 대조에서 강하게 지지되지 않았다. **정답을 후보에 강제로 포함한 표현 비교**이며 48,235개 전체 청킹 검색 정확도가 아니다. 전체 인덱스의 추가 후보·중복·지연을 시험하지 않았고 다른 청킹 크기·집계 방법까지 배제하지 않는다.

## 4. 반대 가설과 구현 오류도 확인

- **지시문 문제:** Qwen의 원래 검색 지시문을 없애면 nDCG 0.2337→0.1795, Hit@5 28→21로 퇴보했다. 제거가 해결책이라는 증거는 없었다.
- **키워드 검색이면 충분한가:** 같은 전체 문서의 BM25는 질문 본문을 추가해도 Hit@5 22→26이었다. 문서까지 제목만 검색하면 제목 질의는 15/91, 본문 질의는 30/91이다. 이 데이터에서는 BM25만으로 높은 검색률을 얻지 못했다.
- **캐시·정규화·순위 오류:** 두 모델의 48,510개 벡터를 검사했고 파일 hash·차원·유한값·단위 norm이 정상이다. 원래 계산 순서로 재현한 두 모델의 상위 100개는 각각 91/91 일치했다. Qwen 질문 91개를 재인코딩한 최소 cosine은 0.99999988이었고 주 지표도 일치했다. 기존 MiniLM 제목 재호출 결과도 일치했다.
- 새 진단의 첫 CPU 검사는 batched 행렬곱으로 계산해 한 질문의 81·82위가 약 1e-7 차이로 뒤집혔다. 원래의 정규화·행렬-벡터 계산으로 맞추니 전부 일치했다. 초기 진단 코드와 수정 기록을 보존했다. 이 차이는 주 지표에 영향이 없으며 기존 평가 버그로 보고하지 않는다.
- **정답표 문제:** 고정 표본에서 Ubuntu 연결 표시 문제와 오프라인 업데이트 문제는 정답 ID 외의 반환 문서도 내용상 관련 있어 보였다. 반면 FreeBSD 다운로드 도구가 Ubuntu 패키지 오류 대신 나온 명백한 주제 차이도 있었다. 정답 누락과 실제 검색 실패가 공존할 수 있다. 답변이나 복구 결과까지 검토하지 않았고 정답표를 바꾸지 않았다.

## 운영에 대한 의미

당장 근거가 있는 우선순위는 **오류 문구·대상·환경·증상을 검색 입력에 보존하는 것**이다. 모델 교체보다 먼저 확인할 대상이다. 이번 본문 추가는 그 방향을 지지하지만 서비스에 그대로 적용한 시험은 아니다.

현재 로컬 코드의 search_rag는 LLM이 만든 자연어 문자열을 받아 상위 5개를 검색한다. 알람과 해결 기록이 함께 들어가며 검색 요청에 type/outcome 필터가 없다. 이 구현상의 사실이 이번 공개 질문 점수의 원인이라는 뜻은 아니다. 실제 서비스의 질의가 필요한 정보를 얼마나 잃는지, 해결 기록 필터가 도움이 되는지는 실제 호출·관련 기록으로 별도 검증해야 한다. 운영 코드는 변경하지 않았다.

기존 공개 질문 자료는 **검색 스트레스 시험**으로 유지할 가치가 있다. 서비스 적합성을 판단하려면 그와 별도로 실제 알람 입력→관련 해결 기록을 연결한 평가가 필요하다. 데이터 전체를 버리거나 정답을 느슨하게 바꿔 점수를 올리는 방향은 근거가 부족하다.
