# RAM/GPU 미수집 오답 수정

## 원인

실제 Prometheus 수집은 정상이었다. 대화 로그에서 봇이 `list_metrics(filter="memory, gpu")`를 호출했고, 기존 구현은 이를 단일 정규식 문자열로 검색해 결과가 없었다. 봇은 빈 검색 결과를 수집 중단으로 잘못 설명했다.

검색 수정 후 실제 대화 검증에서 추가 실패를 발견했다. 모델이 없는 라벨 `job="node"` 또는 `job=~"node"`를 임의로 붙였다. 실제 exporter job은 `node-exporter`다. GPU에도 `job=~"dcgm"`을 붙여 없는 결과를 만들었다. 프롬프트 경고만으로는 이 행동이 고쳐지지 않았다.

## 변경

- 메트릭 검색은 쉼표·공백·파이프로 나눈 OR 검색, 대소문자 무시. RAM/램/메모리는 memory, GPU/VRAM/NVIDIA는 gpu 및 DCGM으로 확장한다.
- 키워드는 리터럴 정규식으로 처리하고 PromQL 문자열도 별도로 이스케이프한다.
- 빈 목록을 수집 실패의 근거로 쓰지 않도록 도구 응답과 대화 지침을 수정했다.
- `get_hardware_status` 읽기 도구 추가. RAM total/available, GPU util, VRAM used/free의 고정된 5개 메트릭을 instant query로 조회한다. 모델이 메트릭 이름과 라벨을 만들지 않는다.
- RAM 사용량과 비율은 코드에서 계산한다. RAM은 GiB, VRAM은 MiB, GPU 사용률은 %로 명시하고 수집 대상 instance와 GPU 모델을 표시한다.
- 한 메트릭의 조회 실패를 전체 수집 실패로 설명하지 않는다. 대화 에이전트는 RAM/GPU 질문에 전용 도구를 우선 사용한다.

## 검증

- 기존 검색 구현에서 신규 회귀 테스트 3개 실패를 확인한 뒤 수정.
- 기본 Java 테스트 **61개 통과**, 실패·오류 0개. 하드웨어 고정 조회의 수치·단위와 OR/별칭/리터럴 검색 테스트 포함.
- 실제 Prometheus가 이스케이프된 검색식을 받아 90개 메트릭을 반환하고 RAM/GPU/VRAM 이름을 포함함을 확인했다.
- 실제 ConversationAgent + 윈도우 qwen3:8b + 실제 Prometheus를 사용해 동일 질문 `램이랑 gpu는?` 시험. 초기 잘못된 라벨 실패를 잡았고 최종 전용 도구로 통과했다.
- 최종 시험 답변: `램은 15.46 GiB 중 7.05 GiB(45.6%)가 사용 중이고, GPU 사용률은 0.0%이며 VRAM 사용량은 61 MiB입니다.` 수치는 시험 시점 값이다.
- 명령 실행기 호출 없음, Discord 시험 메시지 전송 없음. 운영 앱 이미지를 기존 Dockerfile로 빌드하고 재생성했다.
- 독립 검토에서 일부 메트릭의 NaN/Inf 값이 전체 조회를 중단시킬 수 있음을 발견했다. 정상 RAM + GPU NaN, RAM 가용량 Inf + 정상 GPU 회귀 테스트가 수정 전 실패했고, 항목별 검증·제외 후 전체 테스트가 통과했다. GPU 사용률 범위와 DCGM 오류 sentinel도 검증한다.

Windows PC는 추론 서버이며 위 수치는 Prometheus가 수집하는 홈서버 자원이다. Windows 자원 모니터링을 새로 구축한 작업은 아니다. 배포 시 대화 세션은 메모리에 있으므로 새로 시작된다.
