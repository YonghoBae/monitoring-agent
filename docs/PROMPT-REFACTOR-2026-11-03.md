# 관제 에이전트 프롬프트·도구 실행 리팩토링

작성일: 2026-11-03. 소스 반영 및 검증 결과를 기록한다. 실행 중 컨테이너 재배포는 수행하지 않았다.

## 반영 사항

- 대화 프롬프트의 RAM/GPU 사례별 중복 지시를 제거하고 공통 정책과 대화 모드 문맥을 리소스로 분리했다.
- 완료·부분 결과·확인 불가·대상 확인·승인 대기를 구분하도록 정책을 정리했다.
- 요청별 공통 실행 가드를 도입했다. 기본 도구 호출 12회, 시간 90초이며 Reflection 재분석도 같은 예산을 사용한다.
- AgentTools·ConversationTools·WebSearchTool에 동일한 호출 제한을 적용한다. 동일 인자의 읽기 결과는 같은 요청에서 재사용하며 새 요청에서는 다시 조회한다.
- 입력 JSON의 공백·키 순서가 달라도 같은 조회로 인식한다. 캐시 반환도 호출 예산을 소비해 모델의 반복 루프가 무한히 유지되지 않게 한다.
- 도구 관측은 status/source/observed_at/data를 포함한다. 빈 결과·조회 실패·인자 오류·부분 결과·거부·승인 대기를 구분한다.
- Prometheus 메트릭 탐색과 범위 조회의 서비스 오류를 빈 결과로 숨기지 않는다.
- Loki 연결·API 실패도 빈 로그와 구분한다. 로그·과거 사례 본문에 있는 ‘조회 실패’ 문구를 현재 조회의 실패 상태로 오인하지 않는다.
- 중지된 컨테이너의 과거 로그 조회를 허용한다. 실행 중 목록에 없다는 이유만으로 로그 조회를 막던 전제 조건을 제거했다.
- Docker 목록 조회의 시간 초과·비정상 종료를 빈 목록으로 숨기지 않는다. 전체 상태 조회에서는 이 실패가 다른 자원 결과를 지우지 않게 한다.
- CPU·디스크·네트워크 정형 조회를 추가했다. 전체 상태 조회는 RAM/GPU와 실행 중 컨테이너 목록도 포함한다. 실행 중이라는 사실만으로 서비스 health를 보장하지 않는다.
- list_misc는 모델 노출에서 제거했다. 기존 Java 호출용 호환 메서드는 유지했다.
- 승인 대기 안내는 실제 execute_command의 결과를 기준으로 하며 저장된 명령·대상·이유를 표시한다. 다른 읽기 도구가 승인 대기 문자열을 반환해도 승인 상태로 취급하지 않는다.
- 명령과 이유가 비어 있으면 승인 저장 전에 거부한다. 거부된 요청이 나중에 yes로 실행될 수 없도록 실제 승인 저장소를 사용한 회귀 테스트를 추가했다.
- 알람 분석용 v4 후보를 추가했다. v1/v2/v3는 비교 자료로 보존했다.

## 기존 평가가 있었는가

있었다. `eval-dataset-v2.yml`의 38개 알람 시나리오와 `LiveEvalRunner`가 존재했다.
실제 모델이 도구를 선택하고 고정된 Prometheus/Loki/RAG mock을 조회한 뒤, 별도 Judge가 4개 차원으로 채점하는 방식이다.
기존 기본 설정은 2개 프롬프트 × 38개 시나리오 × 3회 = 228개 에이전트 실행과 Judge 채점이다.

이번 변경도 이 데이터셋을 실행해야 한다. 대화 13개가 통과해도 자동 알람의 원인 분석·조치 권고가 회귀할 수 있기 때문이다.
반대로 기존 데이터셋만으로 Discord 후속 질문·새 턴 재조회·승인 문구를 모두 검증할 수도 없다. 두 평가를 함께 유지한다.

## 검증

### 단위·프로토콜 검사

- 기본 테스트 전체 81개 통과.
- 실제 Spring AI 클라이언트에 무한 도구 호출을 반환하는 모의 HTTP 모델을 연결했다. 호출 예산 2회에서 종료하고 실제 읽기는 1회만 수행하는 것을 확인했다.
- 기한 초과 뒤 새 도구 호출 차단, 재분석 공유 예산, 승인 후 추가 호출 차단, 인자 순서가 다른 중복 요청, JSON 문자열 반환값 정규화를 검증했다.
- 빈 이유의 승인 요청 결함은 먼저 실패하는 테스트로 재현한 뒤 수정했다.

### 실제 모델 대화 검사

- 초기 12개 표본: 5개 통과·7개 실패.
- 변경 후 13개 표본: 모두 통과. 명령 문법 설명과 전체 상태 범위를 추가 검증했다.
- 실제 Prometheus를 이용하는 하드웨어 대화 smoke도 통과했다. 명령 실행과 Discord 발송은 mock 또는 미사용이다.
- 정형 CPU·디스크·수신·송신 쿼리를 실제 Prometheus에 직접 실행해 모두 success와 유효한 시계열을 확인했다.
- 문자열·도구 호출 계약 위주 검사다. 통과한 답변의 모든 문장이 의미적으로 정확하다는 보장은 없다.

### 38종 알람 데이터셋

전체 76건을 완료했다. Judge 파싱 실패는 아래 표에서 실패로 포함했다.

| 항목 | v1 | v4 후보 |
|---|---:|---:|
| 통과 / 전체 | 19 / 38 | 17 / 38 |
| 통과율 | 50.0% | 44.7% |
| Judge 파싱 실패 | 0 | 1 |
| 평균 도구 호출 | 5.92 | 2.24 |
| 최대 도구 호출 | 12 | 7 |
| 평균 분석 지연 | 15.64초 | 12.76초 |
| p95 분석 지연 | 20.06초 | 17.18초 |

두 버전 모두 통과한 시나리오 12개, v1만 통과 7개, v4만 통과 5개, 둘 다 실패 14개다.
v4는 호출 수와 지연이 줄었지만 품질 개선 근거가 없으므로 **자동 알람 기본값으로 채택하지 않았다**. 기본값 v1을 유지한다.
대화 프롬프트 정리와 공통 실행 제한·승인·오류 처리 개선은 소스에 반영했다.

후속 [연구 사례 비교 검토](EVALUATION-RESEARCH-COMPARISON-2026-11-03.md)에서 키워드 기반 mock의 정확성, 일부 정답의 관측 가능성, 합격 판정의 한계를 확인했다. 위 숫자는 해당 평가 조건에서의 결과이며 실제 운영 정확도나 프롬프트의 일반적인 우열을 뜻하지 않는다. v4 보류는 검증 부족 상태의 기본값 전환을 피한 결정이며, v4가 일반적으로 열등하다는 확정 판정은 아니다.

v4의 잔여 문제에는 알람 유효성만 확인하고 관련 로그·추가 메트릭 조사를 일찍 끝내는 경우,
미확인 데이터를 수집 실패로 확대 표현하는 경우, 관측값을 잘못 해석하는 경우가 있었다.
따라서 이번 결과로 ‘대부분의 알람 상황에서 정확하다’고 주장할 수 없다. 현재 로컬 모델의 자동 분석 품질은 추가 개선이 필요하다.

원본 산출물: `build/eval/run-20261103-154818/`의 results.jsonl, conditions.json, summary.md, human-grading.md, human-grading-key.csv.
기존 summary.md는 파싱 실패 레코드를 점수 통계에서 제외하므로 v4 분모가 37이다. 위 표는 분모 38을 유지한다.

실행 조건:

- 운영 라우터 경로, 요청 모델 qwen3:8b, temperature 0, maxTokens 1536.
- v1/v4 각 38개 시나리오 × 1회, 총 76건. 모든 arm에 현재 공통 실행 제한 적용.
- Gemini 평가 키가 현재 설정에서 확인되지 않아 같은 로컬 모델/엔드포인트를 Judge로 사용했다.
- 같은 모델 Judge의 자기 선호 편향 때문에 독립적인 품질 검증으로 해석하지 않는다. 1회 실행은 전체 시나리오 탐색이며 통계적 우월성 입증이 아니다.
- 새 정형 조회 도구의 mock 연결 오류가 있던 앞선 중단 실행은 비교에서 제외했다.

## 적용 경계와 남은 검증

- 소스 변경과 컨테이너 배포는 구분한다. 이번 작업에서는 운영 컨테이너를 재배포하지 않았다.
- v4는 평가 후보로 보존한다. 회귀가 관찰돼 추가 대규모 반복·기본값 전환은 진행하지 않았다.
- 독립 Judge 또는 사람 채점, 각 시나리오 3회 이상 반복, fallback 모델의 별도 전체 평가는 남아 있다.
- 도구 상태 분류에는 기존 문자열 응답과의 호환 처리가 포함된다. 새 도구가 반환 형식을 추가하면 상태 계약 테스트도 함께 추가해야 한다.
- 시간 한도는 응답 대기를 종료하고 새 도구 호출을 막는다. 이미 진행 중인 외부 I/O의 즉시 취소는 HTTP 클라이언트와 공급자의 인터럽트 처리에 달려 있다. Prometheus·Loki 요청에는 별도 연결·읽기 타임아웃, Docker 목록 조회에는 프로세스 시간 제한을 설정했다.
- 더 큰 의도 분류기·대화 메모리 구조 교체는 적용하지 않았다. 기존 경로 안에서 종료·승인·오류 처리를 개선했다.

실행 방법과 평가 산출물 형식은 [EVAL.md](EVAL.md)에 기록했다.
