# 벡터 검색 평가: 출처 기반 통제 데이터와 실제 측정 결과

2026-11-17. 홈서버 에이전트가 **과거 해결 기록을 찾는 검색 단계**를 평가했다. 운영 답변 정확도나 자율 복구 성공률을 측정한 결과가 아니다. 첫 통제 평가이며, 운영 코드는 변경하지 않았다.

## 포트폴리오에 쓸 핵심

> 과거 장애 해결 기록을 검색하는 RAG를 평가하기 위해 공식 문서·공개 이슈 16개를 근거로 20개 장애 유형의 통제 데이터셋을 만들었다. 해결 기록 20개와 조치 없는 알람 기록 20개를 구성하고, 한국어 직접 질문·한국어 바꿔쓴 질문·영어 질문 60개 및 정답 없는 질문 8개로 검색을 측정했다. 실제 all-minilm 임베딩과 격리 pgvector를 사용했고, 정답 문서 ID를 실행 전에 고정해 LLM Judge 없이 Recall@5·MRR·nDCG를 계산했다. 현재 방식 재현의 Recall@5는 46/60, 해결 기록 필터는 48/60, BM25는 56/60, RRF 혼합은 53/60이었다. 한국어 표현 변화와 알람/해결 기록 혼합이 약점임을 확인했으며, 단순 혼합이 항상 개선을 보장하지 않는다는 결과도 보존했다.

이 문장은 **통제 데이터에 대한 실험 결과**로 사용한다. 운영 검색 성능을 93.3%로 개선해 배포했다거나 검증된 공개 벤치마크에서 우승했다는 뜻으로 바꾸면 안 된다. 질문·관련성 정답은 한 AI 작성 컨텍스트에서 구성했으며 독립적인 사람 관련성 검수는 수행하지 않았다. 본인과 AI의 실제 작업 분담도 구분해 설명한다.

## 1. 기존 구현에서 무엇을 평가했나

`AlertVectorService`는 알람 이름·메시지·요약을 ` | `로 연결해 저장한다. 해결 기록은 알람 이름·요약·조치·`outcome=...`를 연결한다. `search_rag`는 두 유형을 함께 검색해 상위 5개를 돌려주며, 질문이 해결법을 요구해도 해결 기록으로 한정하는 필터가 없다.

평가에서는 이 텍스트 구성, `all-minilm` 모델, cosine 검색, top-5 정책을 재현했다. Spring AI 1.1.0의 Ollama 구현은 `document.getText()`를 임베딩하고, PgVectorStore의 기본 거리는 cosine이다. 실제 임베딩과 pgvector SQL 검색을 수행했지만 Spring AI 서비스를 통과한 전체 애플리케이션 실행은 아니다. 운영 ANN/HNSW 인덱스의 성능도 측정하지 않았다.

- [Spring AI 1.1.0 Ollama 구현](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.0/models/spring-ai-ollama/src/main/java/org/springframework/ai/ollama/OllamaEmbeddingModel.java)

## 2. 데이터셋은 무엇을 근거로 만들었나

| 구성 | 수량 | 의미 |
|---|---:|---|
| 장애 유형 | 20 | 자원·DB·프록시·네트워크·인증서·알림·미디어 서버 |
| 해결 기록 | 20 | 출처의 절차를 적용해 작성한 합성 해결 사례 |
| 알람 기록 | 20 | 같은 문제를 설명하지만 조치가 없는 혼동용 문서 |
| 정답 있는 질문 | 60 | 유형마다 한국어 직접·한국어 바꿔쓰기·영어 질문 각 1개 |
| 정답 없는 질문 | 8 | 현재 문서 집합에 해결 기록이 없는 근접·외부 주제 |
| 근거 출처 | 16 | 공식 매뉴얼·진단 방법론·공개 Postgres 이슈 |

범위는 컨테이너 OOM·CPU quota, 디스크 공간·inode·I/O 포화, pg_dump 호환성·초기 SQL 권한·vacuum, MySQL 느린 질의, 인증서 갱신, NGINX 요청 제한·WebSocket, Docker 포트 충돌·매핑, DNS, systemd 실행 경로, 시간 동기화, Alertmanager 설정·전송, Jellyfin 변환이다.

자료는 **기존 벤치마크에서 가져온 자연 발생 사고 데이터가 아니다.** 매뉴얼 기반 새 통제 사례이며, `outcome=RESOLVED`도 합성 설정이다. 공개 Postgres 이슈 역시 장애 원리만 적용했다. 실제 운영 DB의 기록을 읽거나 복사하지 않았다.

각 문서에 `source_id`, 각 유형에 관련성 판단 이유를 저장했다. 질문은 과거의 해결 방법을 요청하므로 해당 조치를 포함한 해결 문서 1개를 정답으로 정했다. 같은 증상을 설명하는 알람 문서는 해결 방법을 제공하지 않아 이 과제에서는 정답이 아니다. 일반적인 '비슷한 알람 찾기' 과제로 바꾸면 관련성 기준도 달라져야 한다.

## 3. 방법과 지표

검색 평가의 query/corpus/qrels 구성과 지표 선택은 [BEIR](https://github.com/beir-cellar/beir)와 [Sentence Transformers 검색 평가 문서](https://www.sbert.net/docs/package_reference/sentence_transformer/evaluation.html)를 참고했다. **BEIR 데이터나 공식 BEIR 점수는 아니다.** 혼합 검색은 [Reciprocal Rank Fusion 원 논문](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)의 순위 결합 방식에 근거했다.

| 방식 | 후보 문서 | 순위 계산 |
|---|---|---|
| 현재 방식 재현 | 알람+해결 40개 | all-minilm cosine |
| 해결 기록만 벡터 검색 | 해결 20개 | 동일한 임베딩·cosine |
| BM25 | 해결 20개 | k1=1.2, b=0.75 |
| RRF 혼합 | 해결 20개 | 벡터·BM25 전체 순위를 같은 가중치, 상수 60으로 결합 |

BM25는 영문·숫자 토큰과 한글 글자 bigram을 사용한다. 형태소 분석기나 학습된 한국어 검색기가 아니라 명시적인 경량 비교 기준이다. 정답을 보고 파라미터나 사전을 조정하지 않았다. RRF도 결과를 본 뒤 가중치를 튜닝하지 않았다.

- **Recall@5**: 정답 해결 문서가 상위 5개에 포함됐는가. 질문당 정답이 1개이므로 이 시험에서는 Hit@5와 같다.
- **MRR@5**: 정답 순위가 5 이내이면 `1/순위`, 아니면 0.
- **nDCG@5**: 정답 순위가 5 이내이면 `1/log2(순위+1)`, 아니면 0. 단일 이진 정답인 이 데이터에 해당하는 식이다.
- **Hit@1**: 첫 결과가 정답인가.

주 지표는 정답 있는 60개 질문의 Recall@5다. 각 유형이 3개 질문을 가지므로 유형 가중치는 같다. 같은 유형의 표현을 바꾼 질문은 독립 장애가 아니며, 전체 홈서버 모집단의 신뢰구간이나 유의성을 주장하지 않는다. 정답 없는 8개는 별도 진단으로만 보고한다. 모든 기준은 [사전 프로토콜](../eval/vector-v1/protocol.json)에 저장했다.

## 4. 실제 결과

| 방식 | Recall@5 | Hit@1 | MRR@5 | nDCG@5 |
|---|---:|---:|---:|---:|
| 현재 방식 재현 | 46/60 (76.7%) | 18/60 (30.0%) | 0.4997 | 0.5676 |
| 해결 기록만 벡터 | 48/60 (80.0%) | 39/60 (65.0%) | 0.7011 | 0.7255 |
| BM25 | 56/60 (93.3%) | 48/60 (80.0%) | 0.8547 | 0.8745 |
| RRF 혼합 | 53/60 (88.3%) | 40/60 (66.7%) | 0.7358 | 0.7720 |

여기의 **76.7%는 새 검색 시험의 46/60**이다. 이전 에이전트 답변 평가에서 언급한 76.7점과 무관하며 서로 비교하지 않는다.

질문 유형별 Recall@5:

| 방식 | 한국어 직접 질문 | 한국어 바꿔쓴 질문 | 영어 질문 |
|---|---:|---:|---:|
| 현재 방식 재현 | 20/20 | 8/20 | 18/20 |
| 해결 기록만 벡터 | 20/20 | 8/20 | 20/20 |
| BM25 | 20/20 | 19/20 | 17/20 |
| RRF 혼합 | 20/20 | 14/20 | 19/20 |

직접 질문은 알람 이름과 핵심 용어를 포함하는 쉬운 조건이다. 이 조건의 높은 점수만으로 자연어 검색 품질이 좋다고 주장하면 안 된다. 반대로 바꿔쓴 한국어 질문은 이 모델·이 문서 구성에서 약점을 드러냈다. 언어와 문서 스타일이 함께 영향을 줄 수 있으므로 임베딩 모델 하나만을 원인으로 확정하지 않는다.

## 5. 확인한 실패와 개선 방향

**문서 유형 혼합.** 현재 방식의 긍정 질문 상위 5개 중 31.3%는 해결 기록이 아닌 알람 문서였다. 해결 기록으로 후보를 제한하면 Hit@1이 30.0%에서 65.0%로 바뀌었다. 다만 전체 검색을 무조건 해결 기록으로 제한하기보다, 질문이 알람 유사성인지 해결법인지 구분하는 설계가 필요하다.

영어 질문 20개에서 현재 방식의 첫 정답은 0개였지만, 해결 기록으로 제한하면 16개였다. 알람 문서에는 영어 오류 메시지가 있고 해결 기록은 한국어 설명 중심이므로 언어와 문서 유형이 얽힌 결과다. 이를 영어 검색 자체가 불가능하다는 결론으로 확대하지 않는다.

**한국어 표현 변화.** 예를 들어 '웹사이트 자물쇠 인증서 유효기간이 곧 끝나는데 자동 연장이 안 돼'라는 질문에서 정답 해결 기록은 현재 방식 17위, BM25 1위였다. '실시간 소켓이 한동안 메시지가 없으면 프록시에서 끊긴다'는 질문에서는 24위와 1위였다. 실제 문서 ID와 순위는 [질문별 결과](../eval/vector-v1/runs/initial/results.json)에 남겼다.

**혼합 검색의 역효과 가능성.** 한국어 바꿔쓰기에서 BM25는 19/20, RRF는 14/20이었다. 약한 순위를 그대로 결합하면 좋은 순위가 내려갈 수 있다. 이번 결과를 본 뒤 상수를 바꿔 더 좋은 점수만 보고하지 않았다. 후속 후보는 다국어 임베딩과 별도 개발 세트의 결합 정책 검증이다.

**정답 없음 처리.** 정답 문서가 없는 8개 질문에도 네 방식 모두 문서를 반환했다. 선택한 top-k 정책에서 나온 결과이며, 실제 사용자의 무정답 질문 분포나 최종 에이전트의 환각률을 측정한 것은 아니다. 검색 점수 임계값 또는 재판정 절차는 별도 개발 데이터로 검증해야 한다.

## 6. 검증과 재현

- 데이터·정답·설정·실행 코드·모델 digest를 검색 전에 고정했다.
- 모델은 로컬 `all-minilm:latest`, 384차원, 23M/F16이다. 원문 입력은 잘리지 않도록 `truncate=false`로 요청했다.
- 실제 PostgreSQL 16.16 / pgvector 0.8.7에서 정확 cosine 검색 136개를 실행했다. 운영 DB에 접근하지 않고 네트워크·스토리지가 분리된 임시 컨테이너를 사용했다. 컨테이너는 종료 후 제거했다.
- 저장한 108개 임베딩으로 Python cosine 순위를 독립 계산했으며 136개 전체 순위가 같았다. 최대 점수 차이는 약 `1.25e-7`이었다.
- 지표·관련성 계약·SQL 출력 파싱 등 오프라인 테스트 9개를 통과했다. 별도 검증기는 저장된 결과 272개와 16개 지표 그룹을 다시 계산한다. 지표 산술과 파일 무결성 검증이며, 정답 관련성의 독립 인증은 아니다.
- 최초 실행은 PostgreSQL JSON 출력의 줄바꿈 처리에서 실패했다. 순위·점수 집계 전에 파서를 수정했고, 이전 시도는 로컬에 보존했다. 데이터·질문·정답·검색 파라미터를 바꾸지 않았다.
- 유료 API 호출은 0회다. 서버 자원·전력·개발 시간 비용이 0이라는 뜻은 아니다. 워밍된 모델의 임베딩 108개 처리는 약 1.15초였지만 운영 질의 지연 지표로 사용하지 않는다.

## 7. 면접에서 받을 질문

**왜 LLM Judge를 안 썼나?** 검색 단계에는 미리 정한 정답 문서 ID와 순위가 있어 산술로 평가할 수 있다. 답변 생성의 근거 충실성 평가는 별도의 문제다.

**정답은 누가 만들었나?** 공개 문서의 문제·조치와 통제 시나리오의 요청 목적에 따라 작성자가 매핑했다. 독립 사람 검수는 없으므로 라벨의 객관성이 완전히 인증됐다고 말하지 않는다.

**왜 BM25가 더 좋았나?** 이 작은 고정 문서 집합에서 키워드와 한글 부분 일치가 유리했고 벡터 방식은 한국어 바꿔쓰기에서 약했다. 문서 언어·길이·용어 분포가 달라지면 결과도 바뀔 수 있다. 일반적인 BM25 우월성을 주장하지 않는다.

**실제로 개선했나?** 필터·BM25·RRF 후보를 실험 코드에서 비교해 개선 방향을 찾았다. 운영 `search_rag`에 배포하거나 운영 효과를 입증한 것은 아니다.

**무엇이 아직 부족한가?** 자연 발생 질의·사건 데이터, 다중 관련 문서와 불완전한 관련성 판단, 독립 검수, 문서 수 증가에 따른 검색 성능, 운영 ANN, 해결 실패 기록, 무정답 판단, 검색 결과를 받은 에이전트의 실제 답변 품질은 별도 검증이 필요하다.
