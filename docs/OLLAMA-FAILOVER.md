# Ollama 원격 우선 및 로컬 대체 연결

모니터링 앱에 적용 완료.

| 우선순위 | 서버 | 모델 |
|---|---|---|
| 1 | Windows `127.0.0.1:11434` | `qwen3:8b` |
| 2 | 홈서버 `ollama:11434` | `qwen3.5:4b` |

앱의 OpenAI 호환 연결은 내부 `http://ollama-router:8081`을 사용한다. 임베딩은 기존 홈서버 Ollama의 `all-minilm`을 유지한다. 라우터의 호스트 공개 포트는 없다.

## 전환 동작

- 윈도우 연결 실패·끊김·읽기 시간 초과, HTTP 404/408/429/5xx, 잘못된 완료 응답이면 홈서버 모델로 같은 요청을 보낸다.
- 윈도우 실패 후 15초 동안은 로컬로 바로 보낸다. 이후 들어오는 요청부터 윈도우를 다시 시도하므로 PC 복구 시 자동 복귀한다.
- 연결 시간 제한 2초, 원격 읽기 제한 45초, 로컬 읽기 제한 180초. 읽기 제한은 소켓 무응답 시간이며 전체 요청의 절대 마감시간은 아니다.
- 다른 4xx는 잘못된 요청을 숨기지 않고 반환한다. 두 모델 모두 실패하면 503 오류를 반환한다.
- 비스트리밍 chat completions만 지원한다. 현재 앱은 `.call()`을 사용한다.
- 에이전트 전체를 재실행하지 않고 개별 모델 HTTP 요청만 재전송한다. 이미 실행한 도구의 결과·대화 이력은 보존한다.
- 로그에는 선택한 서버·모델·상태만 남기고 프롬프트·도구 인자·인증 정보는 기록하지 않는다.

## 실제 검증 — 2026-11-03 KST

- 윈도우 원격 모델 응답: HTTP 200, `qwen3:8b`, 약 3.49초.
- 별도 검증 라우터의 원격 주소를 연결 불가 주소로 설정하고 실제 홈서버 모델 응답 확인: HTTP 200, `qwen3.5:4b`, 약 8.40초. 검증 라우터 제거 완료.
- 최종 라우터의 원격 도구 호출 응답: HTTP 200, `qwen3:8b`, 약 0.38초.
- Python 기능·회귀 테스트 11개 통과. 원격 선호·타임아웃·끊김·쿨다운·원격 복귀·도구 이력 보존·양쪽 실패·잘못된 응답 형식 포함.
- 기본 Java 테스트 전체 재실행 통과. 기존 `MockBean` 폐기 예정 경고 등은 남아 있다.
- 앱의 적용 주소와 모델, 라우터 healthy 및 앱 정상 기동 확인. 활성 경보와 수집 실패 0건.

윈도우 PC 자체를 끄거나 실제 장애 알림을 보내지는 않았다. 원격 복귀는 제어된 HTTP 백엔드로 검증했다. 검증 이후 새 실제 경보 전체 처리는 아직 관찰하지 않았다.

## 운영 확인

- 라우터 상태: 컨테이너 내부 `GET http://127.0.0.1:8081/health`. primary/fallback 성공 횟수와 쿨다운 잔여 시간을 제공한다. 이는 프로세스 상태이며 두 모델의 상시 정상 여부를 보장하지 않는다.
- 로그: `rtk proxy docker logs --tail 50 monitoring-agent-ollama-router`.
- 회귀 테스트: `rtk proxy python3 -m unittest discover -s scripts/tests -v`.
- 서버 및 모델 변경은 Compose의 `PRIMARY_OLLAMA_URL`, `PRIMARY_OLLAMA_MODEL`, `FALLBACK_OLLAMA_MODEL` 변수로 설정한다.

남은 제약: 쿨다운 종료 시 동시 요청 여러 개가 원격 재시도를 할 수 있다. 윈도우는 Tailscale·Ollama가 실행돼 있고 11434 연결이 허용돼 있어야 한다.

## 2026-11-03 청크 전송 오류 수정

실제 알람 `932` 분석에서 HTTP 413 `Request body missing or too large`가 발생했다. 데이터가 4MB를 넘었다는 증거가 아니라, 라우터가 `Content-Length`만 읽고 Spring AI의 `Transfer-Encoding: chunked`를 빈 본문으로 오인한 버그였다. 앞선 curl 테스트는 Content-Length를 전송해 이 호환성 문제를 잡지 못했다.

수정 및 검증:

- 청크 본문을 제한된 크기로 디코딩하고, 누적 4MiB 한도를 유지한다. 프레이밍 충돌·잘린 청크·잘못된 헤더와 트레일러는 거부한다.
- 빈 본문·전송 방식 누락·크기 초과 오류를 구분한다. 거부 사유를 본문 없이 로그에 남긴다.
- 청크 요청 회귀 테스트에서 기존 413을 재현했고 수정 후 통과했다. Python 전체 14개 통과.
- 앱과 같은 실제 Spring AI OpenAiChatModel 클라이언트의 선택 실행 테스트를 추가했다. 수정 전 같은 413 실패, 수정 후 실제 윈도우 `qwen3:8b` 응답 성공.
- 기본 Java 테스트 54개 및 선택 실행 Spring 클라이언트 테스트 1개 모두 통과. 독립 코드 검토에서 중요 결함 없음.
- 최종 재배포 후 실제 청크 HTTP 요청도 200, `qwen3:8b`, `OK` 응답을 확인했다.

추가로 새 라우터에 설정했던 CPU 0.5코어 한도가 평균 사용량 약 0.04코어에서도 실행 구간의 약 59%를 제한해 `ContainerHighThrottleRate` 경보를 유발했다. 불필요한 CPU 한도를 Compose에서 제거하고 재생성 후 `NanoCpus=0`, `CpuQuota=0`을 확인했다. 128MiB 메모리 제한과 로그 순환은 유지한다. 기존 5분 평균 경보는 과거 샘플이 빠질 때까지 남을 수 있다.

과거 실패 메시지나 저장된 분석 오류를 삭제하지 않았고, Discord에 테스트 메시지·재분석 알림을 보내지 않았다. 이번 확인은 실제 Spring 클라이언트에서 모델 응답까지이며, 이후 새로운 운영 알람의 전체 처리는 별도 관찰이 필요하다.
